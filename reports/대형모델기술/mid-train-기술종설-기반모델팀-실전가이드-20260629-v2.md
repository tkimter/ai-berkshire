## 사용 안내 / 주선 지도

이 글은 처음부터 읽어야 하는 문헌 종설이 아니라 gate-driven 착수 핸드북이다. 오늘 mid-train 착수 회의를 연다면 먼저 0.2, 0.3, 8, 9를 읽는다. 데이터와 실험을 설계한다면 4.2-4.6, 6, 11을 읽는다. 훈련에서 이미 사고가 났다면 바로 7을 읽는다. 공개 자료와 인용 경계를 검증하려면 2, 3, 12를 읽는다.

## 0. 요약

**Mid-train은 post-train의 확대판이 아니며, pretrain을 단순히 한 구간 더 돌리는 것도 아니다.** 이 글은 보수적인 엔지니어링 정의를 채택한다:

> Mid-train은 base pretrain 이후, SFT/RL 등 post-train 이전에 수행하는 통제된 계속 훈련 구간으로, 모델의 능력 분포, 컨텍스트 적응 능력, 그리고 이후 SFT/RL이 활용할 수 있는 훈련 가능성을 바꾸는 데 쓰인다.

공개 자료 가운데 OLMo 2는 base pretraining 이후, post-training 이전 단계를 명시적으로 mid-training이라 부른다. Qwen3, DeepSeek-V3, Qwen2.5-1M 등의 보고서는 이 단어를 항상 쓰지는 않으며 pre-training, continued pre-training, context extension 또는 long-context pre-training이라 부른다. 이 글은 엔지니어링 의미에서만 이 단계들을 mid-train-like 범주에 넣으며, 원 보고서의 용어와 동일시할 수 없다.

자료 선택에서 이 글은 모델 역사를 복기하지 않는다. 각 모델 계열은 최신 공개 기술 보고서를 우선 읽는다. 직전 버전이 현재 버전으로 대체되지 않는 정보, 예컨대 1M context, 명시적 mid-training 명명, annealing 또는 synthetic data 세부 사항을 공개한 경우에만 직전 버전이나 필요한 예외를 남긴다. 프로젝트를 실행할 때는 먼저 목표 모델 계열의 최신 보고서로 이 글의 과거 표본을 교체해야 한다.

실무적으로 신규 팀은 대규모 훈련부터 쫓을 것이 아니라 먼저 소형 모델 ablation, 데이터 버킷 검증, 오염 검사, base 회귀 평가를 하고, 그다음 주 모델 단기 훈련으로 방향을 검증하며, 고정된 post-train recipe로 이득이 남는지 확인해야 한다. **Mid-train의 성공 기준은 어떤 base benchmark의 상승이 아니라, 능력이 강화되고 망각이 통제되며 post-train 이후에도 이득이 존재하는 것이다.**

경계 측면에서 이 글은 모든 continued pretraining을 mid-train과 동일시하지 않으며, DCA, YaRN, sparse attention, chunked prefill 같은 추론·아키텍처 기법을 단순히 훈련 배합으로 분류하지도 않는다. 공개 사례는 설계 참고로만 쓸 수 있고 recipe로 그대로 베낄 수 없다.

본문의 데이터 비율, token budget, 90일 로드맵, 품질 게이트, 사고 runbook은 모두 신규 팀을 위한 엔지니어링 출발 제안이며, 공개 논문이 직접 제시한 범용 결론이 아니다.

post-train 경험이 있고 mid-train을 맡을 준비를 하는 기반 모델 팀에게 **가장 중요한 것은 곧바로 대규모 훈련에 들어가는 것이 아니라 먼저 네 가지를 세우는 것이다**:

1. **목표 능력과 희생 불가 능력을 명확히 한다**: 예컨대 수학 향상이 범용 대화, 사실 지식, 다국어 능력의 큰 퇴화를 대가로 해서는 안 된다.
2. **소형 모델과 단기 ablation을 한다**: 먼저 데이터 버킷, 학습률, 시퀀스 길이, 오염 통제, 망각 위험을 검증한다.
3. **mid-train 전용 평가를 구축한다**: pretrain loss만 봐서도 안 되고, post-train 이후의 리더보드만 봐서도 안 된다.
4. **Post-train DRI가 이어받아 검증하게 한다**: mid-train의 성공 기준 중 하나는 SFT/RL 이후에도 이득이 남고 훈련이 더 통제 가능해지는 것이지, base checkpoint의 zero-shot 점수 몇 개가 더 좋아지는 것만이 아니다.

### 0.1 독자 의사결정 트리: 어떤 종류의 mid-train을 해야 하는가

| 목표 | 우선 경로 | 1차 라운드 실험 | 핵심 평가 | 처음부터 하지 말 것 |
| --- | --- | --- | --- | --- |
| 수학, 코드, STEM, 복잡한 QA | Capability mid-train | 소형 모델 데이터 mix + 낮은 LR 단기 훈련 | 목표 능력 향상 + 범용 능력 후퇴 | 동시에 128K/1M까지 늘리기 |
| 32K/128K 긴 컨텍스트 | Context extension | 단계적 길이 확장 + 장문서 데이터 버킷 | 다중 증거, 장문서, 긴 코드 과제 | needle-in-a-haystack만 보기 |
| RL reasoning 상한 | Reasoning substrate mid-train | base에 이미 edge-of-competence가 있는지 검증 | 고정 RL/RLVR recipe 이어받기 비교 | RL을 능력의 원천 자체로 취급하기 |
| 수직 도메인 능력 | Domain continued pretraining | 낮은 비율의 도메인 데이터 + 범용 보전 데이터 | 도메인 과제 + 범용 회귀 | 단일 도메인 말뭉치로 훈련을 가득 채우기 |
| Coding agent / tool use | Code/FIM/trajectory mid-train | FIM, repo-level completion, 다중 파일 위치 찾기 | repo task, 편집 과제, post-train 이후 agent eval | 상호작용 형식을 전부 mid-train으로 앞당기기 |

이 의사결정 트리는 실행의 입구이지 배타적 분류가 아니다. 성숙한 프로젝트는 결국 capability shaping, long-context adaptation, post-train readiness를 동시에 포함할 수 있지만, **1차 라운드에서는 주가설 하나만 검증하는 것이 가장 좋다**.

### 0.2 첫날 어떻게 착수하는가

오늘 당장 mid-train 프로젝트를 착수해야 한다면 **훈련부터 열지 않는다. 첫날에는 7가지만 한다**:

1. Model, Data, Training Infra, Eval, Post-train, Safety/Compliance, Product/Domain의 DRI를 한자리에 맞춘다.
2. 한 장짜리 Mid-train charter를 쓴다: 목표 능력, 희생 불가 능력, 왜 반드시 mid-train에서 해야 하는지, 예산 경계.
3. eval registry의 v0 owner와 schema를 동결한다. 훈련 전에 v1 eval registry를 다시 동결하며, base eval, 전용 eval, 긴 컨텍스트 eval, 비공개 holdout, 사람에 의한 샘플 검토를 포함한다. v1이 없으면 Gate 1에 들어가지 않는다.
4. Post-train DRI가 paired protocol의 v0 owner와 schema를 동결하게 한다. 훈련 전에 v1 paired protocol을 다시 동결하며, SFT/RL 데이터 버전, 훈련 예산, seed, harness, 평가셋, 실패 판정을 포함한다.
5. 실험 대장 schema를 만들고, 대장이 없는 실험은 결론에 넣지 않는다고 규정한다.
6. Gate 0-5의 통과 조건, 차단 조건, 서명자를 정의한다.
7. 첫 주에 해서는 안 되는 일을 명확히 한다: 비공개 holdout을 보면서 파라미터를 조정하지 않는다, 같은 실험 ID 아래에서 mix/필터/eval 버전을 바꾸지 않는다, proxy의 성공을 주 모델의 필연적 성공으로 취급하지 않는다.

## 1. 용어 경계: mid-train이란 무엇인가

### 1.1 실용적 정의

이 글은 용어 결벽증식 정의가 아니라 엔지니어링 정의를 채택한다:

> Mid-train은 base pretrain 이후, post-train 이전의 계속 훈련 단계다. 여전히 주로 언어 모델링 목적함수 또는 그 변형을 쓰지만, 데이터, 학습률, 시퀀스 길이, 능력 목표는 이미 "세계 텍스트의 최대 커버리지"에서 "고품질 능력 조형"으로 옮겨가 있다.

이 정의는 몇 가지 공개 실무를 포괄한다:

- late-stage pretraining / annealing: 더 낮은 학습률에서 고품질 데이터로 계속 훈련해 더 낮은 손실과 더 강한 다운스트림 능력을 추구한다.
- domain / capability continued pretraining: 코드, 수학, STEM, 의학, 법률, 금융, 다국어 등의 능력을 중심으로 계속 훈련한다.
- long-context extension: 원래의 base context 위에서 32K, 128K, 256K 등으로 확장하며 위치 인코딩, attention 최적화, 장문서 데이터를 함께 갖춘다. 목표가 1M급 컨텍스트라면 훈련 길이, 위치/attention 외삽, chunked prefill, KV cache, serving 비용을 따로 검증해야 하며, 단순한 계속 훈련이나 데이터 배합으로 적을 수 없다.
- reasoning-oriented mid-train: 수학, 코드, 합성 추론, 교재식 데이터, QA/CoT 등으로 base model을 이후의 RL 또는 RLVR에 더 적합하게 만든다.

Mid-train과 continued pretraining은 겹치지만 강조점이 다르다. continued pretraining은 "훈련을 어디서부터 이어 돌리는가"를 기술하고, mid-train은 "왜 돌리는가, 어떤 데이터로 조형하는가, post-train에 어떻게 기여하는가"를 더 강조한다.

### 1.2 post-train과의 분업

Post-train 팀은 mid-train을 "더 많은 SFT 데이터" 또는 "조금 더 이른 SFT"로 생각하기 쉽다. 이는 위험하다. 둘의 최적화 대상이 다르기 때문이다.

Mid-train이 주목하는 것:

- 모델 내부에 문제 해결에 필요한 지식, 알고리즘 패턴, 표현 능력이 있는가.
- 긴 컨텍스트에서 위치 인코딩, attention, 검색, 구간 간 귀납이 쓸 만한가.
- 코드, 수학, 도구 궤적, 복잡한 지시의 기초 분포가 모델 파라미터에 들어갔는가.
- 이후의 SFT/RL이 능력을 더 쉽게 끌어낼 수 있는가.

Post-train이 주목하는 것:

- 지시 준수, 답변 스타일, 안전 거부, 선호 순위.
- 다중 턴 대화와 사용자 의도 정렬.
- 추론 과정이 겉으로 드러나는가, 제품 전략에 부합하는가.
- RL/RLHF/RLAIF/RLVR에서 reward로 최적화 가능한 행동.

거칠게 말하면 mid-train은 능력 도달 가능성과 파라미터 내 분포를 바꾸는 쪽에, post-train은 과제 인터페이스, 행동 정책, 제품 표현을 바꾸는 쪽에 더 가깝다. 다만 reasoning, tool use, agent, 긴 컨텍스트 과제에서는 둘이 겹치므로 paired protocol로 이득이 어디서 오는지 판단해야 한다.

### 1.3 모든 훈련을 mid-train이라 불러서는 안 된다

이 글은 다음 경우를 단순히 mid-train으로 분류하지 않는다:

- 처음부터 시작하는 대규모 범용 사전훈련.
- 오로지 정렬, 안전 또는 형식을 위한 SFT.
- post-train 데이터 위에서 언어 모델링만 계속 돌리고 능력 목표, 데이터 통제, 회귀 평가가 없는 경우.
- RAG, 외부 도구, 추론 시 search 등 모델 파라미터를 바꾸지 않는 시스템 엔지니어링.

경계가 분명해야 한다. 그렇지 않으면 팀은 post-train의 평가와 조직 방식으로 mid-train을 관리하게 되고, 결국 이득이 어디서 왔는지 판단하기 어려워진다.

### 1.4 post-train 경험이 있는 기반 모델 팀을 위한 10가지 차이 인식

1. **Mid-train의 대상은 능력 분포이지 답변 스타일이 아니다.**
2. Mid-train의 주 손실은 보통 여전히 언어 모델링 목적함수에 가깝고, 선호 최적화가 아니다.
3. Mid-train 데이터에는 QA/CoT/FIM이 포함될 수 있지만 **SFT 데이터를 통째로 앞당기지 않는다**.
4. **Mid-train의 좋은 checkpoint가 반드시 loss가 가장 낮은 checkpoint인 것은 아니며**, 능력 향상과 망각 사이의 Pareto 점이다.
5. **Mid-train의 이득은 base eval과 post-train readiness에서 동시에 관찰해야 한다.**
6. **데이터 오염은 mid-train에서 SFT보다 더 위험하다**. base 능력 판단에 들어가기 때문이다.
7. 합성 데이터는 먼저 검증되고 계층화되어야 하며, "싸다"는 이유로 비율을 높여서는 안 된다.
8. 긴 컨텍스트 능력은 훈련 길이, 추론 외삽 길이, 온라인 서비스 가능 길이를 구분해야 한다.
9. **RL의 이득은 보통 base가 이미 갖춘 도달 가능 능력 구간에 의존하며**, 모든 reasoning 문제를 RL에 떠넘길 수 없다.
10. **훈련 확대 전에 반드시 중단 조건이 있어야 한다**. mid-train은 "예산이 아직 남았으니 계속 돌리는" 것이 아니다.

## 2. 공개 증거의 강약 계층화

공개 자료는 완전히 일치하지 않는다. 가장 틀리기 쉬운 지점은 "보고서가 명시한 훈련 단계", "연구자의 귀납", "인터뷰 속 업계 경험"을 뒤섞는 것이다. 이 글은 증거 강약과 모델 버전의 신구라는 두 축으로 자료를 쓴다. 같은 모델 계열은 최신 버전을 우선하고 많아야 직전 버전까지만 본다. 더 이른 자료는 대체 불가능한 증거가 있을 때만 예외로 삼는다.

### 2.0 이 글의 증거 라벨

공개 사실과 엔지니어링 추론이 섞이지 않도록 이하에서는 기본적으로 네 종류의 증거 라벨을 쓴다:

| 라벨 | 의미 | 쓸 수 있는 곳 | 쓸 수 없는 곳 |
| --- | --- | --- | --- |
| 보고서 사실 | 기술 보고서, 논문 또는 공식 자료가 직접 공개한 단계, token, context, 데이터 유형, 훈련 목표 | 어떤 팀이 실제로 무엇을 했는지 기술 | 다른 팀이 같은 배합을 그대로 베껴야 한다는 추론 |
| 논문 귀납 | 종설이나 통제 실험이 제시한 메커니즘, taxonomy, 변수 관계 | 내부 ablation 설계, 가설 수립 | 산업급 훈련 법칙으로 곧바로 격상 |
| 엔지니어링 귀납 | 이 글이 여러 사례에서 뽑아낸 보수적 실무 제안 | 프로젝트 절차, gate, 대장, 위험 통제 수립 | 어떤 보고서의 원문 결론이라고 주장 |
| 검증 대기 가설 | 인터뷰, 블로그, 업계 통념 또는 소표본 실험이 시사한 방향 | 소형 모델/단기 실험 후보에 편입 | 주 모델 확대 결정에 편입 |

독자는 이 글을 쓸 때 "보고서 사실"을 사실 기반으로, "논문 귀납"과 "엔지니어링 귀납"을 실험 설계의 입력으로, "검증 대기 가설"을 backlog로 삼아야 한다. 대규모 훈련 예산을 소모하는 모든 결정은 팀 자신의 data manifest, eval registry, post-train paired protocol로 돌아가야 한다.

### 2.1 강한 증거: 기술 보고서가 명시적으로 공개한 단계 설계

강한 증거란 모델 팀이 기술 보고서에서 직접 공개한 훈련 단계, token 규모, 컨텍스트 길이 또는 데이터 전략을 가리킨다.

| 사례 | 사용 등급 | 보고서 원용어 | 공개 보고서가 직접 뒷받침하는 것 | 이 글의 엔지니어링 유추 |
| --- | --- | --- | --- | --- |
| Qwen3 | 주독 | pre-training stages | General / Reasoning / Long Context 세 개의 pre-training stage. 총량 약 36T, reasoning-stage tokens 약 5T, 32K 긴 컨텍스트 훈련 | mid-train-like capability shaping + context adaptation |
| DeepSeek-V3 | 주독. 같은 계열의 새 보고서가 나오면 교체 | long context extension | 14.8T base pre-training 이후 YaRN으로 각 1000 steps씩 두 구간의 4K -> 32K -> 128K context extension 수행 | mid-train-like long-context extension. 다만 주로 길이 단계화 결론을 뒷받침 |
| GLM-4.5 | 주독 | mid-training | 23T pre-training 이후 약 1.1T mid-training tokens, 명시적으로 세 하위 단계로 구분: repo-level code(~500B, 4K→32K), synthetic reasoning(~500B), long-context + agent(~100B, →128K). MoE 355B/32B | 명시적 mid-training 명명 + 다중 하위 단계 능력 조형 + 점진적 context extension. MoE 아키텍처에서의 mid-train 참고 표본 |
| Qwen2.5-1M | 직전 버전 전용 보존 | long-context pre-training / post-training / inference scaling | progressive long-context pre-training, 긴 컨텍스트 post-training, DCA/YaRN 외삽, 희소 어텐션과 chunked prefill 배포 최적화 | context adaptation + inference/deployment 협동 표본 |
| OLMo 2 | 필요한 예외 | mid-training | pretraining -> mid-training -> instruction/preference tuning의 명확한 계층 구분. Dolmino Mix, 50B/100B/300B, micro-annealing 등 세부 사항이 비교적 투명 | 좁은 의미의 mid-training 공개 참고 표본 |
| Phi-4 | 필요한 예외 | pretraining / midtraining / post-training | 합성 데이터가 pretraining/midtraining/post-training 전체를 관통. midtraining이 4K context를 16K로 확장함을 명시 | synthetic-heavy training strategy + context extension 경계 표본 |
| Llama 3 | 격하 참고 | initial pre-training / long-context pre-training / annealing | 405B가 15.6T tokens에서 initial pre-training, 약 800B tokens의 long-context pre-training으로 128K까지, 마지막에 40M tokens annealing | late-stage continued pre-training과 annealing의 보수적 참고 |

이 보고서들은 "단계 설계"의 존재를 뒷받침할 수 있지만, 보통 "데이터 비율이나 학습률을 그대로 베끼는 것"을 뒷받침하지는 못한다. 공개되지 않은 tokenizer, 데이터 정제, 샘플링 전략, 기초 checkpoint 상태, 옵티마이저 상태, 시스템 구현이 모두 결과에 뚜렷한 영향을 미친다.

### 2.2 중간 증거: 종설과 통제 실험의 귀납

Mid-training survey, PRISM, 그리고 pre-training / mid-training / RL interplay 같은 연구는 팀이 변수 관계를 이해하도록 돕는다: 데이터 보존과 능력 전이, 능력이 모델의 도달 가능 경계에 있는지, RL이 mid-trained checkpoint에서 이득을 얻을 수 있는지 등이다.

이 연구들의 가치는 메커니즘 가설과 실험 차원을 제시하는 데 있으며, 곧바로 외삽할 수 있는 산업 배합을 주는 데 있지 않다. 특히 통제된 synthetic task나 소규모 모델에서의 결론은 "모든 대형 모델의 훈련 법칙"으로 곧바로 격상할 수 없다.

### 2.3 약한 증거: 인터뷰, 블로그, 업계 통념

인터뷰와 블로그는 보통 두 종류의 정보를 준다: 실무자가 용어를 어떻게 쓰는지, 그리고 팀이 훈련 단계의 조직 논리를 어떻게 기술하는지다. 그러나 이런 자료는 실패한 실험, 데이터 세부 사항, 엔지니어링 제약을 자주 생략하므로 추세 배경으로만 쓸 수 있고 확고한 사실로 쓸 수 없다.

인터뷰가 어떤 단계를 "매우 중요하다"고 주장하면 이 글은 그것을 검증 대기 가설로 취급한다. 기술 보고서, 재현 가능한 실험 또는 팀 내부 ablation이 뒷받침한 뒤에야 훈련 결정에 들어간다.

### 2.4 공개 자료에서 뽑아낸 보수적 공통 인식

첫째, mid-train-like 단계는 보통 base 능력이 형성된 뒤, post-training 이전에 일어난다. Qwen3, DeepSeek-V3, GLM-4.5가 주독 표본이다. Qwen2.5-1M, OLMo 2, Phi-4, Llama 3는 각각 직전 버전 전용, 필요한 예외 또는 격하 참고다. 그중 GLM-4.5와 OLMo 2는 mid-training 용어를 명시적으로 쓰며, GLM-4.5는 한 걸음 더 나아가 mid-training을 code / reasoning / long-context 세 하위 단계로 쪼갰다. 현재 공개 보고서 가운데 하위 단계 구분이 가장 세밀한 표본이다.

둘째, Qwen3, OLMo 2, Phi-4, Llama 3 등의 사례에서 late-stage / continued pre-training은 흔히 더 강한 데이터 스크리닝, 능력 지향 샘플링 또는 고품질 데이터 비중 상향을 수반한다. 그러나 DeepSeek-V3 같은 context extension 사례는 주로 단계적 길이 확장을 뒷받침하며 데이터 배합 결론을 직접 뒷받침하지 않는다. 더 온당한 표현은 이렇다: 후기 token의 한계 가치는 단순한 web tokens 추가가 아니라 품질, 배합, 훈련 목표에 더 의존한다.

셋째, 긴 컨텍스트는 RoPE scaling만 바꾸는 것이 아니다. 진짜 긴 컨텍스트 능력은 훈련 데이터, 길이 curriculum, 위치/어텐션 메커니즘, 추론 프레임워크, 평가 과제가 함께 성립해야 한다. DCA, YaRN, sparse attention, chunked prefill 등의 기술은 작용 위치를 구분해야 한다: 일부는 훈련 가능성에 영향을 주고, 일부는 주로 추론 외삽과 배포 비용에 기여한다.

넷째, reasoning mid-train은 "RL이 쓸 수 있는 substrate를 높인다"는 강한 엔지니어링 가설로 삼기에 더 적합하며, 이미 증명된 보편 법칙이 아니다. 비교적 보수적인 표현은 이렇다: base/mid-trained checkpoint가 목표 과제에 대해 풀이 가능성이 전혀 없으면 RL은 보통 능력을 안정적으로 만들어내기 어렵다. 그러나 RL이 진짜 능력 이득을 가져오는지는 pretraining 노출, 과제가 모델 능력 경계에 있는지, reward 설계, 탐색 예산에도 달려 있다.

다섯째, 합성 데이터는 가치가 있지만 공짜 점심이 아니다. Phi-4는 synthetic data가 reasoning 성능에 뚜렷한 영향을 줄 수 있음을 보여주는 동시에, 세계 지식, 표현 다양성, 실제 분포를 보충하려면 여전히 유기적 데이터가 필요함을 일깨운다.

여섯째, 투명한 실험 대장이 단일 지점의 리더보드보다 중요하다. OLMo 2 같은 보고서의 가장 큰 가치 중 하나는 pretraining, mid-training, post-training과 데이터 구성을 나누어 기술해 후발 팀이 자신의 lineage, 버킷별 loss, 회귀 평가를 세우도록 돕는다는 점이다.

일곱째, 공개 보고서는 "일부 성숙한 팀이 단계화된 late-stage training을 채택했다"는 것을 증명할 수 있지만, "어떤 데이터 비율, 학습률 또는 token budget이 범용 최적"임을 증명하는 경우는 드물다. 이 글의 이후 모든 recipe 표는 어떤 모델 보고서에서 복제한 배합이 아니라 탐색 공간과 품질 게이트로 읽어야 한다.

## 3. 공개 사례가 증명할 수 있는 것과 없는 것

이 장은 모델 보고서의 복술이 아니며 recipe의 출처도 아니다. 사례는 "어떤 공개 사실을 내부 점검 항목으로 바꿀 수 있는가"에 답하는 데만 쓰며 버전 선별 규칙을 따른다: 같은 모델 계열은 최신 버전을 우선하고 많아야 직전 버전까지. 더 이른 표본은 보존 이유를 반드시 적는다.

| 사례 / 자료 | 사용 등급 | 왜 남기는가 | 안전하게 귀납할 수 있는 것 | 도출해서는 안 되는 것 | 내부 검증 조치 |
| --- | --- | --- | --- | --- | --- |
| Qwen3 | 주독: 현재/최신 공개 기술 보고서 표본 | General / Reasoning / Long Context 3단계 pre-training 공개 | capability shaping과 context adaptation은 목표를 나눠 관리할 수 있다 | 원 보고서가 mid-training이라 자칭한다거나, 완전한 데이터 배합을 역추론할 수 있다는 것 | 능력 실험과 긴 컨텍스트 실험을 서로 다른 experiment_id로 분리 |
| DeepSeek-V3 | 주독: DeepSeek-V 시리즈 공개 base report 표본. 이후 같은 계열의 새 보고서가 같은 종류의 세부 사항을 공개하면 교체해야 한다 | 14.8T base pre-training 이후의 32K/128K context extension을 공개하고 아키텍처/시스템 협동을 강조 | 긴 컨텍스트는 훈련, 아키텍처, serving, eval을 동시에 검증해야 한다 | context extension이 일반적인 데이터 계속 훈련 recipe와 같다는 것 | offline/online 긴 컨텍스트 일관성과 짧은 과제 회귀 수행 |
| GLM-4.5 | 주독: GLM 계열 최신 공개 기술 보고서 표본 | mid-training 용어를 명시적으로 쓰고, ~1.1T tokens의 세 하위 단계(repo-level code / synthetic reasoning / long-context + agent)와 점진적 4K→32K→128K context extension 공개 | mid-training은 능력 목표에 따라 여러 하위 단계로 쪼개 독립 관리할 수 있다. 합성 추론 데이터와 agent 궤적 데이터는 mid-train 단계에서 주입할 수 있다 | GLM-4.5의 MoE 아키텍처, 하위 단계 token 비율 또는 전문가 라우팅 전략이 dense model에 그대로 맞는다는 것 | 하위 단계별로 experiment_id 분리. MoE는 라우팅 엔트로피와 전문가 부하를 추가로 모니터링해야 한다 |
| Qwen2.5-1M | 직전 버전 전용 보존 | Qwen3는 그 1M context 훈련, 외삽, 배포 세부 사항을 대체하지 않는다 | 훈련 길이, 추론 외삽, 배포 비용, 실제 과제는 나눠서 검수해야 한다 | 1M까지 직접 mid-train하면 된다거나, 순수 추론 기법만으로 충분하다는 것 | training length, serving config, latency/cost, 실제 긴 과제를 나눠 기록 |
| OLMo 2 | 필요한 예외 | mid-training 용어를 명시적으로 쓰고 데이터 혼합, micro-annealing, post-training 계층 구분을 공개 | mid-train은 독립 관리할 수 있고 lineage/eval gate를 유지할 수 있다 | OLMo 2의 Dolmino mix, token 수가 다른 모델에 맞는다는 것 | checkpoint lineage, mid-train scorecard, post-train 전 평가 구축 |
| Phi-4 | 필요한 예외 | synthetic data for pretraining and midtraining을 공개하고, 명시적 midtraining이 4K -> 16K context 확장을 담당 | 합성 데이터에는 verifier, 스타일 다양성, 유기적 데이터의 받침이 있어야 한다 | reasoning 이득을 "합성 CoT mid-train"에 정확히 귀속할 수 있다는 것 | synthetic bucket 검증, 템플릿 반복률, 사람 검수 오류율 구축 |
| Llama 3 | 격하 참고 | late-stage continued pre-training, long-context pre-training, annealing의 공개 세부 사항이 필요할 때만 읽는다 | late-stage 수렴은 고품질 데이터, LR, checkpoint 선택과 묶여야 한다 | Llama 3의 token budget이나 annealing recipe가 소규모 팀의 기본값이라는 것 | annealing을 기본 동작이 아니라 탐색 변수로 취급 |
| PRISM / pre-mid-RL 연구 | 메커니즘 가설. 모델 버전 계보에 속하지 않음 | 통제 실험으로 retention, interaction, RL substrate 문제를 제기 | 메커니즘 가설은 proxy ablation에 들어갈 수 있다 | 산업용 대형 모델의 법칙으로 격상할 수 있다는 것 | paired SFT/RL protocol로 이득 보존 검증 |

이 표의 사용법은 간단하다. 먼저 주독 표본을 읽는다. 현재 모델 보고서가 어떤 핵심 질문을 다루지 않을 때에만 직전 버전이나 필요한 예외를 읽는다. 대상 팀이 Qwen, DeepSeek, Llama 또는 자체 개발 모델 같은 특정 모델 계열을 다룬다면, 내부 자료 묶음은 그 계열의 최신 보고서로 우선 교체하고 직전 버전은 많아야 한 건만 대조용으로 남긴다.

구버전 사례는 세 가지 경우에만 남긴다. 첫째, 현재 버전에 없는 용어나 거버넌스 구조를 제공하는 경우. 예컨대 OLMo 2의 mid-training 계층 구분. 둘째, 전용 능력에 대한 핵심 엔지니어링 분해를 제공하는 경우. 예컨대 Qwen2.5-1M의 1M context 훈련/외삽/배포 분리. 셋째, 아직 새 보고서로 대체되지 않은 통제 변수를 제공하는 경우. 예컨대 Llama 3의 annealing이나 Phi-4의 synthetic data 경계. 그 밖에는 구모델을 주독 목록에 넣지 않는다.

## 4. Mid-train의 설계 프레임워크

이 장은 먼저 1차 라운드 최소 폐루프에 따라 읽는다: Gate 0에서 목표 능력, 희생 불가 능력, eval registry, post-train paired protocol을 동결한다. Gate 1에서 data manifest를 동결한다. Gate 2에서 control mix + 3-5개의 단일 변수 변형으로 proxy scale에서 나쁜 방향을 배제한다. Gate 3에서 target model 단기 훈련으로 능력/망각 Pareto checkpoint를 찾는다. Gate 4에서 동일한 frozen post-train paired protocol로 이득이 남는지 검증한다. 4.1-4.6은 이 폐루프의 목표, 데이터, 훈련 조절 항목, ablation, curriculum, 조직 품질 게이트를 각각 설명한다.

실행 가능한 mid-train 프로젝트는 최종적으로 다섯 가지 질문에 답해야 한다: 목표 능력은 무엇인가, 어떤 능력이 퇴화해서는 안 되는가, 능력은 어떤 데이터 버킷이 이끄는가, 훈련 길이/학습률/context curriculum은 어떻게 설정하는가, 그리고 그것이 post-train에 도움이 됨을 어떻게 증명하는가.

### 4.0 1차 라운드 최소 폐루프

mid-train을 처음 할 때는 완전한 훈련 시스템부터 설계하지 않는다. 여기서 "최소 폐루프"는 최소 훈련 배합이 아니라 최소 증거 사슬이다: 가능한 한 작은 실험 비용으로 데이터, 훈련, 평가, post-train 이어받기가 설명 가능한 결론을 이룰 수 있는지 검증한다. 먼저 목표 하나, 주가설 하나, 데이터 버킷 한 묶음, eval registry 한 벌, 단기 훈련 창 하나, frozen post-train paired protocol 하나를 끝까지 돌려 본다.

| 폐루프 고리 | 질문 하나에만 답한다 | 최소 증거 | 실패하면 어디로 돌아가는가 |
| --- | --- | --- | --- |
| 목표 | 왜 반드시 mid-train이어야 하는가 | 목표 능력, 희생 불가 능력, 대안 배제 | charter로 돌아가 목표를 바꾸거나 mid-train을 하지 않는다 |
| 데이터 | 어느 버킷이 목표 능력을 이끌 수 있는가 | data manifest, 오염 검사, linked eval, 사람 검수 샘플 | 데이터 버킷 진입 카드로 돌아간다 |
| 훈련 | 저위험 단기 훈련에서 방향성 이득이 나타나는가 | LR/mix/context를 고정한 checkpoint 곡선과 버킷별 loss | 훈련 조절 항목 또는 데이터 mix로 돌아간다 |
| 평가 | 이득이 공개 리더보드나 형식에 의한 가짜 양성이 아닌가 | private holdout, raw output, 사람 검토, scorecard | eval registry로 돌아간다 |
| 이어받기 | post-train 이후에도 이득이 남는가 | paired SFT/RL protocol, seed, AUC, 실패 샘플 | post-train recipe 또는 mid-train 목표로 돌아간다 |
| 결정 | extend / rollback / kill 중 무엇인가 | Gate dashboard, evidence_path, owner 서명 | 해당 gate로 돌아간다 |

11장이 제시하는 것은 이 폐루프의 예시 탐색 그리드 한 벌이지 기본 배합이 아니다. 4장은 먼저 설계 대상을 다루고, 6-8장은 증거를 어떻게 판단하는지 다루며, 11장에 이르러서야 실행 가능한 출발 예시를 준다.

### 4.1 능력 목표의 계층화

목표를 네 계층으로 나누기를 권한다:

1계층: 범용 base 보전

- 범용 언어 모델링 loss가 비정상적으로 오르지 않는다.
- 상식, 사실, 다국어, 기초 지시 이해가 뚜렷이 퇴화하지 않는다.
- 다중 턴 대화는 mid-train의 주목표가 아니지만 기본 가독성이 무너져서는 안 된다.

2계층: 핵심 능력 강화

- 수학: GSM8K, MATH, AIME류, 그리고 내부의 검증 가능한 문제은행.
- 코드: HumanEval, MBPP, EvalPlus, repo-level completion, FIM, 다중 파일 위치 찾기 등. SWE-bench는 고정 harness, 가벼운 instruction wrapping 또는 post-train readiness 단계에서 쓰기에 더 적합하다.
- STEM: GPQA, MMLU-Pro, 도메인 문제은행.
- 추론: BBH, ARC, 논리 추론, 복잡한 QA.

3계층: 구조 능력

- 긴 컨텍스트 검색, 종합, 충돌 해소.
- FIM, 코드 완성, 다중 파일 편집.
- 표, 로그, 긴 PDF, 긴 회의록 이해.

4계층: post-train readiness

- SFT 이후 목표 형식을 더 쉽게 익히는가.
- RL/RLVR 이후 더 안정적으로 향상되는가.
- reward hacking이 줄어드는가.
- 추론 궤적이 더 통제 가능한가.

### 4.2 데이터 버킷 설계

적어도 다음 데이터 버킷을 세우기를 권한다:

| 데이터 버킷 | 목표 | 주요 위험 | 권장 통제 |
| --- | --- | --- | --- |
| 고품질 web / book | 범용 언어와 세계 지식 유지 | 노이즈, 중복, 저작권/컴플라이언스 | 중복 제거, 품질 분류, 샘플링 상한 |
| 코드 | 프로그래밍 능력, 형식화 구조 | license, 중복, benchmark 유출 | license 필터링, repo 중복 제거, 문제은행 격리 |
| 수학 / STEM | 추론과 기호 능력 | 경시 문제 과적합, 풀이 오류 | 검증 가능한 문제, 난이도 계층화, proof/answer 검증 |
| 합성 교재 | 개념 압축, 교수식 추론 | 스타일 단일화, teacher 오류 | 다중 teacher, 다중 템플릿, 검증기 필터링 |
| QA / CoT | 추론 궤적과 과제 형식 | post-train 행동을 미리 굳힘 | 비율 통제, 자연 텍스트 유지 |
| 장문서 | 긴 컨텍스트 적응 | 속 빈 padding, 비효율 token | 실제 장문서 + 합성 긴 과제 |
| FIM / 코드 편집 | coding agent 능력 | 일반 LM 분포 파괴 | 버킷별 loss와 코드 eval |
| 도메인 데이터 | 산업/제품 능력 | 파국적 망각, 협소화 | 낮은 비율로 혼입, 범용 회귀 |

전역 mix 하나만 만들지 않는다. 각 버킷에는 다음이 있어야 한다:

- 데이터 출처와 license 기록.
- 중복 제거 전략.
- 품질 점수.
- contamination 검사.
- 샘플링 비율.
- 개별 loss.
- 대응하는 eval.

### 4.2.1 데이터 버킷 진입 카드

각 데이터 버킷은 훈련에 들어가기 전에 곧바로 mix에 들어가는 것이 아니라 먼저 data manifest에 들어가야 한다. 최소 필드는 다음과 같다:

| 필드 | 설명 |
| --- | --- |
| `bucket_id` / `bucket_name` | 데이터 버킷 번호와 이름 |
| `source_manifest` | 원 출처, 시간 범위, license / 컴플라이언스 상태 |
| `processing_commit` | 정제, 파싱, 필터링 스크립트 버전 |
| `dedup_version` | 문서 단위, 문단 단위, 코드 repo 단위, 문제 단위 중복 제거 버전 |
| `contamination_version` | public benchmark, private holdout, 합성 prompt와의 오염 검사 버전 |
| `tokenizer_version` | tokenizer와 special tokens 버전 |
| `quality_score_distribution` | 품질 점수 분포. 평균 점수만 적지 않는다 |
| `language_domain_distribution` | 언어, 도메인, 파일 유형, 길이 분포 |
| `time_distribution` | 데이터 시간 범위, 신구 분포, 훈련 이후의 새 사건 포함 여부 |
| `sampling_weight` | 현재 mix에서의 샘플링 가중치와 상한 |
| `shuffle_seed` / `bucket_interleaving` | 데이터 순서, bucket 교차 배치 전략, 단계적으로 mix를 바꾸는지 여부 |
| `bucket_validation_loss` | 버킷별 validation loss와 이상 변화 |
| `linked_eval_id` | eval registry에서 대응하는 평가 항목 |
| `known_risks` | license, 오염, 템플릿화, 중복, 사실 오류, 분포 협소 |

데이터 버킷 진입 게이트는 강제 규칙으로 적기를 권한다:

> [!CAUTION]
> - **manifest/hash가 없으면 훈련에 들어가지 않는다.**
> - **대응하는 eval이 없으면 샘플링 가중치를 높이지 않는다.**
> - **오염 적중이 처리되지 않았으면 primary 실험에 들어가지 않는다.**
> - **합성 데이터에 정확성 필터링과 스타일 다양성 검사가 없으면 낮은 비율의 탐색을 넘지 않는다.**
> - **도메인 데이터에 범용 회귀 보호가 없으면 주 모델 단기 훈련에 들어가지 않는다.**
> - **긴 컨텍스트 데이터가 이어 붙인 텍스트뿐이고 실제 긴 과제가 없으면 long-context primary mix에 들어가지 않는다.**
> - **필터, 품질 모델, dedup 임계값, 샘플링 가중치, 합성 생성 prompt 또는 데이터 순서를 바꾸는 모든 조치는 새로운 `data_manifest_hash`와 `experiment_id`를 생성해야 한다.**

### 4.2.2 합성 데이터 사용 경계

합성 데이터는 따로 거버넌스해야 한다. 단기 지표에서 "매우 효과적으로 보이기" 가장 쉽기 때문이다:

| 위험 | 양상 | 통제 방식 |
| --- | --- | --- |
| Teacher 오류 증폭 | 수학/코드 답이 유창해 보이지만 검증 불가 | 실행 가능 검증, 답안 검증, 표본 추출 사람 재검토 |
| 스타일 템플릿화 | 출력이 모두 같은 teacher 같고 추론 단계가 고정됨 | 다중 teacher, 다중 prompt, 다중 풀이, 유기적 데이터 혼입 |
| Benchmark 근사 오염 | 공개 문제의 변형이 대량 등장 | 문제 본문, 풀이 구조, embedding, translated duplicate 검사 |
| 난이도 분포 왜곡 | 훈련 문제가 너무 쉽거나 한 가지 유형만 커버 | 난이도 버킷화, 실패 샘플 재투입, 비공개 holdout 대조 |
| CoT 행동의 과도한 앞당김 | base 모델이 장황한 설명 형식을 너무 일찍 익힘 | CoT 비율 통제, 단답, CoT 없는 샘플, 자연 텍스트 혼입 |

**합성 데이터의 합리적 용법은 "검증 가능한 능력 증폭기"이지 저비용 token 대체품이 아니다**. 수학, 코드, 구조화 추론에는 검증 가능한 합성을 많이 쓰기에 적합하다. 개방형 도메인 지식, 언어 스타일, 다국어 표현은 여전히 고품질 유기적 데이터가 받쳐 줘야 한다.

합성 데이터 유형마다 경계도 다르다:

| 합성 데이터 유형 | 적합한 용도 | 부적합한 용도 | 반드시 검사할 것 |
| --- | --- | --- | --- |
| 검증 가능한 수학/코드 | 기호 추론, 실행 가능한 문제 풀이, 단위 테스트 능력 향상 | 개방형 도메인 지식 대체 | verifier, 답안 실행, 난이도 버킷화 |
| 교재식 설명 | 개념 압축, 지식 구조 보완 | 큰 비율로 자연 말뭉치 대체 | teacher 다양성, 표현 템플릿, 사실 표본 검사 |
| CoT / rationale | 추론 궤적 형식 제공 | base가 장황한 답변 스타일을 너무 일찍 굳히게 함 | CoT 비중, 단답 혼입, 스타일 표류 |
| 긴 컨텍스트 합성 과제 | 희소한 긴 과제 패턴 커버 | 실제 장문서와 긴 코드 대체 | 증거 위치, 방해 정보, 답변 불가 샘플 |
| 도메인 합성 QA | 도메인 과제 형태 보충 | 실제 도메인 문서 대체 | 전문가 표본 검사, 출처 추적, 용어 일관성 |

Synthetic bucket은 또한 teacher model/version, 생성 prompt, 샘플링 파라미터, verifier 버전, 필터링 규칙, 거부된 샘플 비율, 템플릿 반복률, 답안 검증 가능률, 사람 표본 검사 오류율, 그리고 생성기가 eval/benchmark를 읽은 적이 있는지를 반드시 기록해야 한다. 합성 CoT/QA는 style entropy, template n-gram, response length distribution을 추가로 검사해 post-train 행동 형식을 미리 굳히지 않도록 한다.

### 4.3 학습률과 token budget

공개 보고서는 보통 모든 세부 사항을 완전히 주지 않지만, 엔지니어링상 몇 가지 견고한 원칙이 있다.

첫째, mid-train은 보통 pretrain 초기에 가까운 높은 학습률을 써서는 안 된다. 모델은 이미 대량의 범용 능력을 형성했고, 지나치게 높은 학습률은 망각, 스타일 표류, loss spike를 부른다.

둘째, 학습률 전략은 목표와 맞아야 한다:

- 단기 능력 강화: 낮은 학습률로 계속 훈련하며 전용 능력과 범용 회귀를 관찰한다.
- late-stage annealing: 학습률을 더 낮추고 고품질 데이터로 수렴시킨다.
- context extension: 학습률을 더 보수적으로 잡고 길이 curriculum과 결합한다.
- domain adaptation: token budget과 데이터 비율을 더 제한해 모델이 좁아지는 것을 피한다.

셋째, token budget은 클수록 좋은 것이 아니다. 아래 세 구간은 착수 실험을 위한 보수적 눈금일 뿐이며, 모델 규모에 따라 선형적으로 통용되지 않고 scaling ablation을 대체할 수도 없다:

- 1B-10B tokens: pipeline, 데이터 품질, LR, 오염 검사, proxy ablation에 쓴다.
- 10B-100B tokens: 관찰 가능한 능력 강화와 중소형 모델 recipe 검증의 예시 구간이다. 실제 예산은 모델 규모, 데이터 품질, gate 결과가 결정해야 한다.
- 100B-1T+ tokens: 주 모델의 비교적 완전한 capability shaping 또는 long-context extension에나 적합하다.

위 내용은 업계 법칙이 아니라 엔지니어링상 비교적 보수적인 출발 눈금이다. 진짜 token budget은 모델 규모, 데이터 품질, 목표 능력, 예산이 함께 결정해야 한다.

### 4.3.1 배합 조절 항목과 동시 변경 금지 원칙

훈련 변수도 데이터와 eval처럼 버전을 동결해야 한다. 매 run마다 적어도 다음을 기록한다:

| 변수 | 왜 동결해야 하는가 | 흔한 오판 |
| --- | --- | --- |
| `base_checkpoint_hash` | 출발점 능력과 기존 데이터 노출을 결정한다 | 서로 다른 base의 차이를 mid-train 이득으로 오판 |
| `optimizer_state_strategy` | 이어받기나 재설정은 loss 곡선과 안정성을 바꾼다 | 재설정 후 warmup 부족으로 생긴 가짜 퇴화 |
| `lr_schedule` / `warmup` | 망각, 수렴, loss spike에 영향을 준다 | 최종 점수만 비교하고 훈련 안정성을 비교하지 않음 |
| `peak_lr` / `min_lr` / `decay_shape` | 실제 최적화 궤적을 결정한다 | 모두 "낮은 LR"이라 부르지만 훈련 동역학은 전혀 다름 |
| `gradient_clipping` / `precision` | 안정성과 수치 오차에 영향을 준다 | 수치 불안정을 데이터 mix 문제로 오판 |
| `global_batch` / `microbatch` | 유효 batch와 훈련 노이즈를 바꾼다 | 작은 batch 노이즈를 능력 변동으로 오판 |
| `sequence_length_distribution` / `length_bucket_ratio` | 유효 token 분포와 훈련 동역학을 바꾼다 | 길이 변화가 가져온 이득을 데이터 mix에 귀속 |
| `data_order` / `shuffle_seed` | curriculum, annealing, 긴 컨텍스트 단계는 순서에 민감하다 | 같은 mix라도 순서가 다르면 정반대 결론이 나옴 |
| `packing_policy` / `masking_policy` | FIM, 장문서, 짧은 샘플 비율에 영향을 준다 | 짧은 과제는 퇴화하는데 전역 loss는 정상 |
| `checkpoint_selection_policy` | 최종 비교 대상을 결정한다 | 사후에 최고 checkpoint를 골라 이득을 과장 |
| `eval_cadence` | 망각과 표류를 언제 발견하는지 결정한다 | 훈련이 끝나고서야 되돌릴 수 없는 후퇴를 발견 |

Scale-up도 보수적이어야 한다. Proxy의 성공은 어떤 방향이 계속할 가치가 있음을 말해 줄 뿐, 목표 규모에서 반드시 성공함을 뜻하지 않는다. 더 큰 훈련에 들어가기 전에 적어도 네 가지 조건을 충족한다:

1. 두 개의 scale 또는 target 단기 run의 방향이 일치한다.
2. 버킷별 loss, 목표 eval, base regression의 변화가 동일한 데이터/훈련 가설로 설명된다.
3. 같은 mix에서 seed가 달라도 결과가 뒤집히지 않으며, 훈련 처리량, checkpoint resume, 모니터링이 이미 검증되었다.
4. 비용상 수용 가능하다: token을 10배로 늘려도 한계적인 소폭 이득밖에 얻을 수 없다면 예산을 늘릴 것이 아니라 먼저 데이터나 eval을 개선해야 한다.

한 번의 실험에서 너무 많은 조절 항목을 동시에 바꾸지 않는다. 흔한 조절 항목을 나눠서 보기를 권한다:

| 조절 항목 | 조정 방식 | 주요 위험 | 관측 신호 | 언제 멈추는가 |
| --- | --- | --- | --- | --- |
| LR / warmup | 낮은 LR, 추가 인하, 짧은 warmup sweep | 망각, loss spike, 수렴 과도 지연 | 전역 loss, 버킷별 loss, 그래디언트 노름 | spike가 회복되지 않거나 보전 지표가 빠르게 하락 |
| Token budget | 단기 예산을 점증 | 예산 낭비, 좁은 분포 과적합 | checkpoint 간 delta, Pareto 곡선 | 한계 이득이 사라지거나 후퇴가 확대 |
| Sequence length | 길이 분포를 단계적으로 늘림 | 긴 훈련이 짧은 과제를 해침, 처리량 하락 | 길이 버킷별 loss, 짧은 과제 회귀 | 짧은 과제가 뚜렷이 퇴화하거나 serving 비용을 수용할 수 없음 |
| Batch / packing | packing 변경, 긴·짧은 샘플 혼합 | 유효 데이터 분포 변화 | 처리량, padding, 짧은 샘플 loss | 전역 loss는 정상인데 버킷별로 이상 |
| Optimizer state | 이어받기 또는 재설정 | 모멘텀 승계 또는 warmup 부족 | early loss, 그래디언트, resume 연속성 | early instability를 설명할 수 없음 |
| Synthetic ratio | 상한을 단계적으로 높임 | 템플릿화, teacher 오류 증폭 | 비공개 eval, 스타일 검토, 실패 샘플 | 스타일 붕괴 또는 비공개 셋에서 상승 없음 |
| Domain ratio | 낮은 비율로 혼입 | 모델 협소화, 범용 능력 퇴화 | 범용 회귀, 도메인 비공개 과제 | 도메인 상승폭이 범용 후퇴의 대가보다 작음 |

### 4.4 1차 라운드 ablation 설계표

1차 라운드에서는 "최고의 배합"을 추구하지 말고 잘못된 방향을 빠르게 배제한다. 아래 표의 비율은 탐색 변수의 예시일 뿐으로, 민감도와 나쁜 방향을 드러내는 데 쓰며 주 훈련의 기본 mix로 삼을 수 없다.

| 실험 목적 | 모델 규모 예시 | Token budget 예시 | 데이터 mix 탐색 변수 예시 | LR 변수 | 성공 지표 | 중단 조건 |
| --- | --- | --- | --- | --- | --- | --- |
| Pipeline과 eval 보정 | proxy model, 예컨대 1B/3B | 1B-3B tokens | 소표본 전 버킷 mix | 낮은 LR 단일 지점 | loss 정상, eval 재현 가능 | loss spike, eval 불안정 |
| 범용 보전 하한선 | proxy model, 예컨대 3B/7B | 3B-10B tokens | 범용 고품질 비중 30/50/70% | 고정 낮은 LR | 범용 능력 후퇴가 통제 가능 | 다국어/사실 급락 |
| 수학/STEM 주입 | proxy model, 예컨대 3B/7B | 5B-20B tokens | 수학/STEM 10/20/30% | 낮은 LR + 더 낮은 LR | 수학이 향상되고 범용이 무너지지 않음 | 공개 문제 유형만 향상 |
| 코드/FIM 주입 | proxy model, 예컨대 3B/7B | 5B-20B tokens | 코드/FIM 10/20/30% | 고정 낮은 LR | completion/FIM/repo task 향상 | 일반 생성이 뚜렷이 코드화됨 |
| 합성 데이터 비중 | proxy model, 예컨대 3B/7B | 5B-20B tokens | synthetic 5/15/30% | 고정 낮은 LR | 검증 가능 과제 향상, 스타일 다양 | 템플릿화 또는 오염 위험 |
| 주 모델 단기 검증 | target model | 10B-100B tokens | 후보 mix 2-3개 | 낮은 LR sweep | Pareto checkpoint 출현 | 목표 능력이 오르지 않거나 망각이 과도 |

이 실험들의 산출물은 최종 모델이 아니라 결정이다: 어느 데이터 버킷이 유효한지, 어느 비율이 위험한지, 어느 학습률 구간이 안전한지, 더 긴 주 훈련에 들어갈 가치가 있는지.

### 4.4.1 ablation을 어떻게 읽는가

Ablation의 산출물은 나쁜 방향의 배제와 후보 Pareto의 형성이지 최종 배합의 증명이 아니다. 다섯 가지 규칙으로 판독하기를 권한다:

1. **Proxy의 성공은 target의 성공과 같지 않다**. 주 모델에 들어가기 전에 두 scale의 방향이 일치하거나 target 단기 run으로 재검증해야 한다.
2. **단일 공개 리더보드의 상승은 능력 강화와 같지 않다**. 반드시 private holdout, 실패 샘플 군집, 사람 검토와 함께 봐야 한다.
3. **Target 능력 향상은 반드시 guardrail과 함께 봐야 한다**. 수학/코드는 오르는데 다국어, 사실, 자연 생성이 뚜렷이 떨어지면 깨끗한 이득이 아니다.
4. 임계값에 가까운 결과는 run을 반복하거나 인접 checkpoint로 재검증한다. **seed 한 번의 소폭 이득으로 확대 결정을 내리지 않는다**.
5. **중간에 mix, filter, LR, 길이 curriculum 또는 eval 버전을 바꾼 모든 실험은 experiment_id를 새로 열어야 한다.**

### 4.5 Curriculum: 능력 먼저 길이 나중인가, 병행인가?

신규 팀은 처음부터 모든 목표를 한데 섞지 않기를 권한다.

더 안정적인 순서는 다음과 같다:

1. Base 보전 점검: checkpoint, tokenizer, optimizer state, 데이터 pipeline, 평가 체계가 쓸 만한지 확인한다.
2. 능력형 mid-train: 수학/코드/STEM/고품질 합성 데이터, 단기 ablation.
3. 긴 컨텍스트 적응: 비교적 짧은 context에서 단계적으로 늘리며 긴 컨텍스트 loss와 실제 과제를 따로 모니터링한다.
4. 소규모 post-train 이어받기: 고정된 SFT/RL recipe로 mid-train 전후 checkpoint를 비교한다.
5. 주 훈련 배합으로 합칠지 결정한다.

왜 능력 먼저 길이 나중을 권하는가? 긴 컨텍스트 훈련은 비용이 높고 debug가 어려우며, 아키텍처 문제와 데이터 문제를 뒤섞기 쉽기 때문이다. 모델의 기초 reasoning/코드 능력이 개선되지 않았다면 긴 컨텍스트는 입력 창을 키울 뿐 과제 능력을 반드시 키우지는 않는다.

예외도 있다: 제품 목표가 바로 법률/금융 장문서 QA나 코드베이스 agent라면 긴 컨텍스트를 앞에 둘 수 있지만, 그래도 먼저 소형 모델에서 검증하기를 권한다.

| 제품 주목표 | 권장 사전 가정 | 1차 라운드 검증 | 반증 신호 |
| --- | --- | --- | --- |
| 수학, 코드, STEM, 복잡한 QA | 능력 먼저, 길이 나중 | 능력 버킷 + 범용 보전 버킷 단기 ablation | 목표 능력이 public benchmark에서만 오르고 private/사람 검수 샘플에서는 오르지 않음 |
| 법률/금융/과학 연구 장문서 QA | 능력과 길이 병행. 다만 실험 ID를 둘로 나눈다 | 능력 단기 훈련 하나, 32K/64K context 단기 훈련 하나 | 긴 컨텍스트 검색은 좋은데 종합/충돌/답변 불가 과제가 나쁨 |
| 코드베이스 agent / repo-level editing | 코드/FIM과 중장 컨텍스트 병행 | FIM/repo task, 긴 코드 위치 찾기, 짧은 코드 회귀 | repo task는 오르는데 일반 코드 생성이나 짧은 과제가 뚜렷이 퇴화 |
| 도메인 계속 훈련 | 먼저 낮은 비율의 도메인, 그다음 길이가 필요한지 본다 | 도메인 버킷 5/10/20% + 범용 회귀 | 도메인 과제 상승폭이 범용 능력 후퇴의 대가보다 작음 |
| 긴 컨텍스트 시연 능력 | 먼저 제품 가치를 확인하고 그다음 context extension | 실제 긴 과제, serving 비용, 짧은 과제 회귀 | NIAH는 보기 좋은데 실제 과제, 온라인 비용 또는 짧은 과제가 성립하지 않음 |

긴 컨텍스트 curriculum은 최대 길이만이 아니라 길이 분포를 기록해야 한다. 각 단계에서 적어도 다음을 기록한다:

- 4K/16K/32K/64K/128K 샘플 비율.
- packing 전략, padding 낭비, 짧은 샘플이 과도하게 업샘플링되었는지 여부.
- 긴 샘플의 출처: 자연 장문서, 긴 코드, 합성 긴 과제, 문서 간 집합.
- 과제 구조: 증거 밀도, 답변 불가 샘플, 충돌 증거, 멀티홉 증거, 증거 위치, 출력 길이.
- 훈련 kernel과 추론 kernel의 일치 여부.

그렇지 않으면 "128K로 확장"은 최대 길이 선언일 뿐, 모델이 긴 컨텍스트 이해를 익혔는지, 장거리 검색을 익혔는지, 아니면 더 긴 입력에서 loss가 무너지지 않게 버티는 법만 익혔는지 설명하지 못한다.

### 4.6 조직 운영 메커니즘: 역할, 대장, 품질 게이트

Mid-train 프로젝트는 훈련 팀이 단독으로 끝내는 모델 이어 훈련이 아니라, data, training, eval, post-train 네 쪽이 같은 실험 대장과 같은 품질 게이트를 공유하는 능력 조형 프로젝트다. 모든 조직 개념은 엔지니어링 객체에 묶여야 한다: checkpoint, data manifest, eval version, gate, owner, decision.

첫째, 막연한 "다중 팀 참여"가 아니라 DRI를 지정한다.

| 워크스트림 | 유일한 DRI | 참여 팀 | 최종 결정 | 핵심 산출물 |
| --- | --- | --- | --- | --- |
| 목표 정의 | Model Lead | Product/Domain, Eval, Post-train | Model Lead | Mid-train charter, 희생 불가 능력, 실험 가설 |
| 데이터 구축 | Data DRI | Research, Safety/Compliance, Eval | Data DRI + Safety/Compliance | 데이터 버킷 설명, data manifest/hash, lineage, contamination report |
| 훈련 실행 | Training Infra DRI | Model, Data, Infra | Training Infra DRI | 훈련 runbook, LR/token budget 설정, checkpoint ledger, 사고 기록 |
| 평가 체계 | Eval DRI | Model, Product/Domain, Post-train | Eval DRI | eval registry, 비공개 holdout, scorecard, 사람 검토 샘플 |
| Post-train 이어받기 | Post-train DRI | Eval, Safety, Model | Post-train DRI | frozen post-train paired protocol, readiness report, 정렬 회귀 |
| 긴 컨텍스트 시스템 | Infra DRI | Training, Eval, Serving | Infra DRI + Eval DRI | kernel/serving 일관성 보고서, KV cache/latency/cost 평가 |
| 위험과 출시 | Safety/Compliance DRI | Data, Product, Release | Decision owner | 컴플라이언스 심사, 위험 등록표, go/no-go memo |

둘째, 실험 대장에는 고정된 schema가 있어야 한다. 대장이 없는 실험은 결론에 들어가지 않는다. 중간에 mix, 필터, eval 버전을 바꾸면 반드시 experiment_id를 새로 만든다.

| 필드 | 설명 |
| --- | --- |
| `experiment_id` / `hypothesis` / `owner` | 실험 번호, 검증할 가설, 유일한 책임자 |
| `base_checkpoint_hash` / `training_code_commit` | 출발점 checkpoint와 훈련 코드 버전 |
| `data_manifest_hash` / `data_bucket_ratio` | 데이터 manifest, 샘플링 가중치, 데이터 버킷 비율 |
| `dedup_version` / `contamination_version` | 중복 제거, 근사 중복, 오염 검사 버전 |
| `lr_schedule` / `warmup` / `optimizer_state_strategy` | 학습률, warmup, optimizer state 이어받기 또는 재설정 |
| `token_budget` / `sequence_length_distribution` | token 예산과 길이 분포. 최대 길이만 기록하지 않는다 |
| `eval_suite_version` / `private_holdout_version` | eval registry, 비공개 holdout, harness commit |
| `seed` / `cost` / `incident_log` | 난수 시드, 훈련 비용, 이상 사건과 처리 조치 |
| `result_summary` / `decision` / `signoff` | 결론 요약, kill/retry/extend/promote 결정, 서명자 |
| `post_train_readiness_result` | 고정 SFT/RL recipe 이후 이득이 남는지 여부 |

셋째, 품질 게이트의 유일한 권위 대시보드는 8.0절에 둔다. 이 절은 역할, 대장 필드, 서명 책임만 정의한다. 이 글이 팀을 대신해 임계값을 정할 수는 없지만 gate memo는 적어도 다음을 정의해야 한다: 목표 능력 최소 향상, 범용 능력 최대 후퇴, 비공개 eval 통과율, 오염 적중률 상한, loss spike 처리 규칙, 스타일 표류 판정, post-train 이후 이득 보존 비율. 모든 gate 상태, 증거 경로, 버전 hash, 만료 시각은 8.0절 dashboard를 기준으로 한다.

| Gate | 진입 조건 | 종료 조건 | 차단 조건 | 서명자 |
| --- | --- | --- | --- | --- |
| Gate 0: charter | 목표 능력, 희생 불가 능력, 예산, post-train 이어받기 수요가 명확 | Mid-train charter 통과. v1 eval registry와 v1 post-train paired protocol 상태는 8.0절 dashboard를 기준으로 한다 | DRI 없음, paired protocol owner/schema 없음, 비공개 holdout owner/schema 없음 | Model Lead, Eval DRI, Post-train DRI |
| Gate 1: 데이터 동결 | 데이터 소스, license, 정제, 중복 제거, 오염 검사 완료 | data manifest/hash 동결, 사람 표본 검사에서 체계적 오류 없음 | benchmark 유출, license 불명확, 합성 데이터 템플릿화가 뚜렷 | Data DRI, Safety/Compliance DRI, Eval DRI |
| Gate 2: proxy ablation | 최소 두 개의 후보 mix와 고정 eval suite | proxy는 나쁜 방향 배제에만 쓴다. 주 모델에 들어가기 전에 두 scale의 방향이 일치하거나 target 단기 훈련으로 핵심 신호를 검증해야 한다 | 공개 benchmark만 오르고 비공개 과제는 움직이지 않음, 범용 능력 급락 | Model Lead, Eval DRI, Data DRI |
| Gate 3: 주 모델 단기 훈련 | 훈련 runbook, resume, 모니터링, kill switch 준비 완료 | 능력/망각 Pareto checkpoint가 나타나고 버킷별 loss가 설명 가능 | NaN, 회복 불가능한 loss spike, 그래디언트 이상, 처리량 이상, resume 불연속, 긴 컨텍스트가 짧은 과제를 해침 | Training Infra DRI, Eval DRI, Model Lead |
| Gate 4: post-train 이어받기 | paired protocol의 recipe, seed, 예산, harness, 실패 판정이 동결됨 | 고정 paired protocol 아래 post-train 이후에도 이득이 남고 안전/스타일에 뚜렷한 악화가 없음 | mid-train 이득이 post-train 이후 사라짐, paired protocol이 중간에 바뀜, 또는 정렬 난이도가 뚜렷이 증가 | Post-train DRI, Eval DRI, Safety DRI |
| Gate 5: 훈련 확대 | 이득의 원천이 설명 가능하고 데이터/eval/훈련 자동화가 안정적 | go/no-go memo 통과, 다음 단계 예산 진입 | 이득이 오염, 좁은 평가, 우연한 checkpoint에 의존하거나 재현 불가 | Decision owner, Model Lead, Release owner |

넷째, 회의 리듬은 보고가 아니라 결정에 봉사해야 한다:

- Daily training review: loss, 처리량, NaN/loss spike, checkpoint, resume, 사고 처리.
- Twice-weekly eval review: 목표 능력, 범용 회귀, 비공개 holdout, 사람에 의한 샘플 검토.
- Weekly decision review: kill, retry, extend, promote. 대장과 gate memo에만 근거해 결정한다.
- Post-train handoff review: paired protocol이 유효한지, 이득이 남는지, 안전과 스타일이 퇴화했는지.

이 메커니즘의 하한선은 이렇다: **달력은 품질 게이트를 대체할 수 없다**. 90일은 참고 리듬일 뿐이며, 다음 단계에 들어갈지는 데이터 준비도, 훈련 안정성, eval 안정성, post-train 이어받기 검증이 결정한다.

## 5. 훈련 엔지니어링 체크포인트

### 5.1 착수 전 점검

mid-train 착수 전에 다음을 끝내야 한다:

- Base checkpoint의 완전한 eval 스냅샷.
- Optimizer state를 이어받을지에 대한 결정.
- Tokenizer와 special tokens 동결.
- 데이터 중복 제거와 benchmark contamination 검사.
- 각 데이터 버킷의 샘플 검토.
- 소규모 dry run으로 loss, 처리량, 메모리, checkpoint, resume이 정상인지 확인.
- Post-train DRI가 이후 SFT/RL의 paired protocol을 확정.

post-train 이어받기 검증이 없으면 mid-train은 잘못된 목표를 최적화하기 쉽다.

### 5.2 훈련 중 모니터링

적어도 다음을 모니터링해야 한다:

- 전역 training loss / validation loss.
- 데이터 버킷별로 분해한 validation loss.
- 범용 능력 benchmark의 회귀.
- 목표 능력 benchmark의 이득.
- 긴 컨텍스트의 길이 구간별 loss.
- 생성 샘플의 스타일 표류.
- MoE 모델의 전문가 부하, 라우팅 엔트로피, token drop.
- 그래디언트 노름, loss spike, checkpoint 간 차이.

**훈련이 끝날 때까지 기다렸다가 eval을 하지 않는다.** Mid-train의 실패는 흔히 초기에 신호가 있다: 범용 eval 급락, 출력 스타일 템플릿화, 어떤 데이터 버킷의 loss 이상, 긴 컨텍스트로 인한 짧은 과제 퇴화.

### 5.3 Checkpoint 전략

다음을 보존하기를 권한다:

- pre-mid checkpoint.
- 각 단계의 early/mid/final checkpoint.
- 학습률 변화 전후의 checkpoint.
- context length curriculum 각 길이 단계의 checkpoint.
- post-train 이어받기에 쓸 후보 checkpoint.

마지막 것만 보존하지 않는다. **Mid-train의 최선 checkpoint는 loss가 가장 낮은 checkpoint가 아니라 목표 능력과 망각 사이의 Pareto 최적점일 수 있다.**

### 5.4 과소평가하기 쉬운 엔지니어링 위험

첫째, mixed-length batching과 context parallelism은 부하 불균형을 가져온다. 긴 컨텍스트 batch의 처리량, 메모리 파편화, padding 낭비, 통신 패턴은 모두 짧은 컨텍스트와 다르다. 훈련 모니터링은 길이 구간별로 쪼개야 하며, 그렇지 않으면 전역 처리량이 국소적 불안정을 가린다.

둘째, optimizer state는 이어받아도 재설정해도 문제가 생길 수 있다. optimizer state를 이어받으면 원래 훈련 궤적의 연장에 더 가깝지만 이전 단계의 모멘텀을 물려받을 수 있다. optimizer state를 재설정하면 더 깨끗하지만 warmup을 다시 설계해야 하며, 그렇지 않으면 loss spike나 지나치게 느린 수렴이 생기기 쉽다. 두 방안 모두 먼저 proxy scale에서 시험해야 한다.

셋째, **훈련 attention kernel과 배포 attention kernel의 불일치는 가짜 양성을 만든다**. 오프라인 eval 통과가 온라인 128K/1M 서비스 가용을 뜻하지 않는다. 긴 컨텍스트 훈련, 추론 외삽, kv cache, chunked prefill, sparse attention, serving 프레임워크는 반드시 합동 검증해야 한다.

## 6. 평가 체계

### 6.0 benchmark list에서 eval registry로

Mid-train의 평가 시스템은 리더보드 모음이 아니라 버전, 오염 상태, 실행 harness, 임계값, 원시 출력 보관을 갖춘 eval object의 집합이다. **registry에 들어가지 않은 평가 결과는 관찰로만 쓸 수 있고 go/no-go 근거로 쓸 수 없다**.

프로젝트마다 primary 지표는 최대 3-5개를 두고, 그 밖에 guardrail과 diagnostic을 몇 개 둔다. Primary가 너무 많으면 cherry-pick을 유도하고, diagnostic이 너무 적으면 팀이 왜 오르내렸는지 알 수 없다.

### 6.1 Eval registry의 최소 schema

Eval DRI는 Gate 0에서 v0 owner와 schema를 동결하고, Gate 1에 들어가기 전에 v1 eval registry를 동결해야 한다. 최소 필드는 다음과 같다:

| 필드 | 의미 |
| --- | --- |
| `eval_id` | 유일 번호 |
| `eval_family` | base regression / target capability / long-context / post-train readiness / safety-style |
| `task_name` | 과제명 |
| `data_source` | public / dev-private / sealed-private / final-blind / synthetic / human-written |
| `created_at` / `data_hash` | 생성 시각과 데이터 hash. 비공개 셋은 대응하는 훈련 데이터 mix 동결보다 앞서야 한다 |
| `split_policy` | dev / private holdout / regression set / final-blind |
| `contamination_check_version` | exact / n-gram / MinHash / embedding / paraphrase / translated duplicate / manual |
| `harness_commit` | 평가 코드 버전 |
| `prompt_or_wrapper_version` | base prompt, minimal prompt, few-shot policy, light instruction wrapper, agent harness 버전 |
| `decoding_params` | temperature, top_p, max tokens, pass@k 등 |
| `metric` / `aggregation` | accuracy, pass@k, F1, judge score, latency/cost 등과 집계 방식 |
| `decision_role` | primary / guardrail / diagnostic |
| `threshold_or_guardrail` | 향상 임계값, 최대 후퇴, 실패 조건, 최소 유의 차이 |
| `sample_size` | 표본 크기와 추출 규칙 |
| `manual_review_rubric` | 사람 검토가 필요할 때의 rubric |
| `raw_output_path` | 원시 출력 보관 위치 |
| `owner_note` | 설명용 비고. 조직 책임은 넣지 않는다 |

Eval 버전 변경 규칙은 못박아 둔다: 샘플, prompt, 답안 추출기, metric, harness, 임계값을 바꾸면 모두 새 `eval_suite_version`을 생성해야 하며, 이전 결과와 가로로 섞어 비교할 수 없다.

비공개 holdout은 세 계층으로 나누기를 권한다:

- dev-private: pipeline 조정, harness 보정에 쓰며 최종 gate에 들어가지 않는다.
- sealed-private: 단계 게이트에 쓰며, 이것을 겨냥해 데이터 mix나 prompt를 조정하는 것을 금지한다.
- final-blind: Gate 5 또는 출시 전에만 쓰며, 반복 최적화되어 "또 하나의 훈련 목표"가 되는 것을 피한다.

### 6.2 Eval suite matrix

| Eval family | 목적 | 대표 과제 | 적용 checkpoint | Metric | 실패 신호 | Raw output 요건 |
| --- | --- | --- | --- | --- | --- | --- |
| Base regression | 희생 불가 능력 보호 | 범용 지식, 다국어, 기초 생성, 사실 QA | pre-mid, mid, post-train 이후 | 최대 후퇴, 저득점 버킷 변화, 사람 검토 | 평균 점수는 소폭 하락인데 특정 언어/스타일이 무너짐 | 고정 샘플 바구니의 완전한 출력 |
| Target capability | 목표 능력이 정말 강해졌는지 판단 | 수학, 코드, STEM, 도메인 과제, FIM | pre-mid, mid | delta, 난이도 버킷, 비공개 과제 통과율 | 공개 리더보드만 오르고 비공개 과제는 움직이지 않음 | 성공/실패 샘플 군집 |
| Long-context | 긴 컨텍스트가 쓸 만한지 판단 | 다중 증거 QA, 충돌 해소, 긴 코드 위치 찾기, 긴 표/로그 | mid, post-train 이후 | 길이 버킷별 성능, 짧은 과제 회귀, latency/cost | needle은 만점인데 실제 과제가 나쁨 | 입력 길이, 증거 위치, backend 설정 |
| Post-train readiness | 이득이 SFT/RL 이후에도 남는지 판단 | 고정 SFT/RL recipe 이후의 실제 과제와 안전 평가 | paired post-train checkpoints | 이득 보존 비율, 훈련 곡선 AUC, 분산 | base는 오르는데 post-train 이후 사라짐 | recipe, seed, checkpoint selection policy |
| Safety/style | 스타일, 안전, 거부의 표류 방지 | 안전 셋, 거부 경계, 중국어 글쓰기, 긴 답변 품질 | mid, post-train 이후 | 회귀율, 사람 rubric, 거부 오적용 | 템플릿화, 장황한 CoT, 환각 증가 | 사람 검토 샘플과 채점 사유 |

목표 능력 eval은 "능력이 정말 강해졌는가"에 답한다. base regression eval은 "다른 능력을 해치지 않았는가"에 답한다. post-train readiness eval은 "이 base 변화가 SFT/RL을 통과하고도 여전히 가치가 있는가"에 답한다.

### 6.3 Base regression eval

Base regression의 요점은 모델이 더 강해졌음을 증명하는 것이 아니라 희생 불가 능력을 보호하는 것이다. 다음을 커버해야 한다:

- 범용 지식: MMLU, MMLU-Pro, 내부 지식 문제.
- 추론: BBH, ARC, GPQA, 논리 문제.
- 수학: GSM8K, MATH, AIME 스타일 내부 문제.
- 코드: HumanEval, MBPP, EvalPlus, repo-level completion, FIM, 다중 파일 위치 찾기.
- 다국어: 중국어, 영어, 목표 시장 언어.
- 생성 품질: 긴 답변, 요약, 설명, 번역, 자연 대화.

Base model은 복잡한 형식을 안정적으로 따르지 않을 수 있으므로 "능력 부족"과 "형식 불복"을 구분해야 한다. 각 base eval은 minimal prompting, few-shot policy, 답안 추출기 버전, 사람 재검토 규칙을 기록해야 한다. SWE-bench, agent 과제, tool-use eval에는 지시 준수, 도구 프로토콜, 환경 안정성, scaffold 품질이 섞여 있어, 맨 base의 주지표보다는 readiness/diagnostic으로 쓰기에 더 적합하다.

Base regression scorecard는 적어도 다음을 보고한다:

- 평균 점수만이 아니라 희생 불가 능력의 최대 후퇴.
- 저득점 버킷과 롱테일 언어의 변화.
- 출력 스타일, 거부, 장황함의 정도, 환각 샘플.
- 고정된 사람 검토 샘플 바구니의 결론.

### 6.4 Target capability eval

Target capability eval은 base regression과 분리해야 한다. "공개 리더보드가 올랐는가"만 묻는 것이 아니라 "목표 능력이 실제 과제와 비공개 과제에서 강해졌는가"를 묻는다.

| 목표 능력 | 평가 방식 | 필요한 방어선 |
| --- | --- | --- |
| 수학/STEM | 난이도 버킷, 검증 가능한 답, 비공개 변형 문제, 실패 샘플 군집 | 경시 문제 근사 중복과 synthetic overfit 방지 |
| 코드/FIM | HumanEval/MBPP/EvalPlus, FIM, repo-level completion, 다중 파일 위치 찾기 | SWE-bench/tool-use는 readiness 또는 diagnostic으로 사용 |
| 도메인 능력 | 도메인 비공개 문제, 실제 문서 QA, 전문가 사람 rubric | 도메인 데이터가 범용 능력을 좁히는 것을 방지 |
| Agent/tool-use | 고정 harness, 환경 버전, 도구 프로토콜, 과제 궤적 | scaffold가 좋아진 것을 base가 강해진 것으로 오판하지 않음 |

목표 능력이 public benchmark에서만 오르고 private holdout, 실패 샘플 군집, 사람 검토가 뒷받침하지 않으면 먼저 오염, 형식 적응 또는 좁은 분포 최적화로 간주해야 한다.

### 6.5 Long-context eval

긴 컨텍스트 평가는 세 계층으로 나눈다:

- 기계적 검색: Needle-in-a-haystack, 다중 needle, 서로 다른 위치와 서로 다른 노이즈 밀도. diagnostic으로만 쓸 수 있고 주 gate에 들어가서는 안 된다.
- 진짜 이해: 장문서 QA, 다중 장 요약, 다중 증거 종합, 충돌 정보 판단, 긴 표/로그 분석.
- 과제 완수: 긴 코드베이스 수정, 다중 파일 bug 위치 찾기, 법률/실적/논문 종합 분석, agent 궤적 복기와 다음 단계 결정.

긴 컨텍스트 eval registry는 반드시 축별로 펼쳐야 한다:

| 축 | 필수 측정 슬라이스 |
| --- | --- |
| Context length bucket | 4K, 16K, 32K, 64K, 128K. 목표가 1M이면 256K/1M을 추가 |
| 과제 유형 | 검색, 요약, 다중 증거 QA, 코드 위치 찾기, 구간 간 추론, 답변 불가 질문 |
| 증거 밀도 | 희소한 사실, 밀집 표, 긴 코드, 충돌 증거 |
| 방해 정보 | 방해 없음, 같은 주제의 방해, 모순 증거, 만료된 정보 |
| 증거 위치 | 앞부분, 중간, 끝부분, 다중 위치 증거 |
| 출력 요건 | 단답, 구조화 표, 긴 답변, 증거 인용 |
| 추론 backend | attention kernel, KV cache, chunked prefill, batching, serving 설정 |
| 비용 제약 | latency, 처리량, 메모리, 요청당 비용 |
| 짧은 과제 회귀 | 짧은 과제를 긴 컨텍스트에 넣었을 때 퇴화하는지 여부 |

긴 컨텍스트의 hard gate는 "최장 길이에서 돌아간다"만 봐서는 안 된다. 더 합리적인 문턱은 이렇다: 짧은 컨텍스트 능력이 뚜렷이 퇴화하지 않고, 중장 컨텍스트 실제 과제에 이득이 있으며, 추론 시스템이 목표 길이에서 비용과 지연을 수용할 수 있다.

### 6.6 Post-train readiness eval

Post-train readiness는 paired protocol을 써야 한다:

- pre-mid checkpoint와 mid checkpoint는 동일한 frozen post-train paired protocol을 쓴다.
- 데이터 순서, seed, 예산, checkpoint selection policy, reward/verifier, harness, decoding, 실패 판정을 고정한다.
- 핵심 결론이 임계값에 가까울 때는 다중 seed 또는 반복 run을 돌리고 분산이나 bootstrapped CI를 보고한다.
- "최고의 post-train checkpoint"로 사후 비교하지 않는다. 고정 예산, 고정 선택 규칙 아래의 결과를 비교하거나 훈련 곡선 AUC를 보고한다.

여기서 동결하는 SFT/RL recipe는 pre-mid와 mid checkpoint를 비교하기 위한 진단 기기이며 최종 생산용 post-train 배합을 뜻하지 않는다. 더 좋은 결과를 얻으려고 recipe를 조정한다면 experiment_id를 다시 등록해야 하며, 원래의 mid-train 결론을 그대로 이어 쓸 수 없다.

| 비교 항목 | 무엇을 보는가 | 실패 신호 |
| --- | --- | --- |
| 수렴 속도 | 같은 예산에서 목표 능력에 더 빨리 도달하는가 | 개별 seed에서만 빨라짐 |
| 최종 능력 | 목표 능력이 post-train 이후에도 남는가 | base는 오르고 post-train 이후 사라짐 |
| Reward 행동 | RL이 reward hacking을 줄이거나 검증 가능 과제를 높이는가 | 장황한 추론, 요행을 노린 형식, 답 표류 |
| 안전/스타일 | 거부 경계, 중국어 표현, 긴 답변 품질 | 안전 회귀, 템플릿화, 거부 오적용 |
| 긴 컨텍스트 | post-train 이후 긴 과제가 계속 쓸 만한가 | SFT 이후 긴 컨텍스트 능력이 덮여 사라짐 |

4분면 판독:

| 결과 | 해석 | 결정 |
| --- | --- | --- |
| base 상승, post-train 이후에도 상승 | 가장 믿을 만한 mid-train 이득 | 확대 후보에 들어갈 수 있다 |
| base 상승, post-train 이후 상승 없음 | base eval 가짜 양성이거나 post-train이 이득을 덮어 버렸을 수 있다 | 데이터/eval로 돌아간다. 곧바로 확대할 수 없다 |
| base 상승 없음, post-train 이후 상승 | 훈련 가능성을 개선했거나 SFT/RL과 상호작용했을 수 있다 | seed 반복과 실제 과제로 검증한다 |
| base 하락, post-train 이후 상승 | 고위험 trade-off | 희생 불가 능력이 훼손되지 않았을 때에만 계속할 수 있다 |

### 6.7 Scorecard: 평가 결과를 어떻게 읽는가

후보 checkpoint마다 한 장짜리 scorecard를 생성해야 한다. 이는 Eval DRI가 gate에 주는 입력이며 4.6의 최종 go/no-go 결정을 대체하지 않는다.

| 필드 | 내용 |
| --- | --- |
| `checkpoint_id` | checkpoint hash, 훈련 스텝 수, token 수, context length |
| `target_capability_delta` | primary 지표 변화, 난이도 버킷 변화, 비공개 과제 변화 |
| `base_regression_max_drawdown` | 희생 불가 능력의 최대 후퇴와 저득점 버킷 변화 |
| `private_holdout_result` | dev-private, sealed-private의 사용 현황과 결과. final-blind는 Gate 5 또는 출시 전까지 unused/reserved로 유지해야 하며, 여전히 손대지 않았는지 기록한다 |
| `long_context_result` | 길이 버킷, 실제 과제, 짧은 과제 회귀, serving 설정 |
| `post_train_readiness_result` | paired protocol, seed, 이득 보존, 분산 |
| `contamination_status` | exact/near-duplicate/embedding/manual 검사 결과 |
| `known_regressions` | 알려진 퇴화, 실패 샘플 군집, 사람 검토 결론 |
| `recommended_action` | kill / retry / extend / promote |

**어떤 지표의 이득이 비정상적으로 높은데 비공개 과제, 사람 검토, 인접 eval이 뒷받침하지 않으면, 능력 돌파를 먼저 선언할 것이 아니라 오염, 형식 적응 또는 과적합을 먼저 가정해야 한다.**

Gate meeting에서는 먼저 한 줄짜리 적·황·녹 요약을 보고, 그다음 완전한 scorecard를 본다:

| 상태 | 의미 | 회의 조치 |
| --- | --- | --- |
| Green | target, guardrail, private holdout, post-train readiness가 같은 방향으로 뒷받침하고 증거 경로가 완전하다 | extend/promote를 논의할 수 있다 |
| Yellow | 이득은 있으나 분산, 후퇴, 오염, post-train 보존 또는 serving 비용이 아직 불분명하다 | owner를 지정해 증거를 보충하고 확대에 들어가지 않는다 |
| Red | 희생 불가 능력이 선을 넘음, 오염/license 미해소, 사고 미귀인, post-train 이후 체계적으로 악화 | rollback/kill, 또는 experiment_id를 새로 연다 |

## 7. 위험과 사고 처리 Runbook

7장은 실패 유형에 대한 교양 설명이 아니라 훈련 중의 사고 처리 runbook이다: 모든 이상은 증상 하나, 실험 ID 하나, 영향받은 checkpoint 하나, 증거 경로 한 묶음, 그리고 계속/롤백/kill 결정 하나로 귀결될 수 있어야 한다.

### 7.0 이 장의 사용법

정상 모니터링, eval registry, gate 메커니즘은 각각 4-6장에 있다. 이 장은 이상만 다룬다. 이상이 발동하면 당직 DRI는 먼저 현장을 동결하고, 30분 1차 진단을 한 뒤, 마지막으로 임시 결정을 내린다. 귀인이 끝나기 전에는 같은 run 안에서 데이터, 학습률, eval harness, post-train recipe를 바꾸지 않는다.

사고가 나면 먼저 세 단계를 밟고, 설정부터 바꾸지 않는다:

| 단계 | 조치 | 출력 |
| --- | --- | --- |
| 1. 현장 동결 | checkpoint, optimizer, data manifest, eval raw outputs, 시스템 지표, 관련 commit 저장 | `incident_id`와 evidence paths |
| 2. 등급 판정 | observation / alert / blocker를 판단하고 30분 1차 조사 owner 지정 | 임시 stop/continue 결정 |
| 3. 계층별 격리 | system replay, data manifest diff, eval harness diff, model checkpoint diff를 차례로 수행 | root cause 또는 unresolved 표시 |

사고는 먼저 여섯 유형으로 등록한다:

| 사고 유형 | 전형적 범위 |
| --- | --- |
| numerical | NaN, Inf, loss 폭발, 그래디언트 이상, 혼합 정밀도 오버플로 |
| data | 데이터 버킷 오염, 형식 표류, license 문제, 합성 데이터 템플릿화, 샘플링 가중치 오류 |
| eval | harness, prompt, judge, metric, 표본 추출 또는 오염으로 인한 점수 이상 |
| infra | 처리량, GPU 사용률, NCCL, 스토리지, checkpoint, serving 설정 이상 |
| capability | 목표 능력이 오르지 않음, 범용 능력 후퇴, guardrail 악화, 긴 컨텍스트 실제 과제 퇴화 |
| post-train handoff | SFT/RL 이어받기 이후 이득 소멸, reward hacking 증가, recipe 노이즈 증폭 |

> [!CAUTION]
> **강제 규칙: 모든 능력 결론이나 훈련 효과 결론은 먼저 4계층 격리를 끝내야 한다**: system replay, data manifest diff, eval harness diff, model checkpoint diff. 어떤 계층이 사고와 무관하면 `N/A`로 표시하고 이유를 적는다. **증거가 갖춰지지 않았을 때는 미귀인 사고로만 등록할 수 있고 능력 결론에 써넣을 수 없다.**

### 7.1 사고 등급: 관찰, 경보, 차단

| 등급 | 발동 신호 | 현장 조치 | 훈련을 계속해도 되는가 |
| --- | --- | --- | --- |
| 관찰 | 단일 eval의 소폭 변동, 버킷별 loss의 경미한 편이, seed 한 번이 임계값에 근접 | incident_id를 기록하고 인접 checkpoint 또는 고정 샘플 바구니를 재실행 | 계속할 수 있으나 promotion은 불가 |
| 경보 | 연속 checkpoint의 지표 이상, public/private 괴리, 어떤 데이터 버킷의 loss가 뚜렷이 이탈, 목표 능력은 오르는데 guardrail이 악화 | 변수를 동결하고 Data/Eval/Training DRI를 불러 30분 1차 조사 | guardrail에 따라 결정. 보통 확대를 중지 |
| 차단 | NaN/Inf, resume 불연속, 오염 또는 license 불명확, 희생 불가 능력이 선을 넘음, 오프라인에서는 쓸 만한데 온라인에서 서비스 불가 | run 또는 출시를 중단하고 가장 최근의 건강한 checkpoint로 롤백한 뒤 사고 복기를 연다 | 계속하지 않는다. 복기 후 experiment_id를 새로 만든 경우는 예외 |

처리 원칙:

| 원칙 | 구체적 방법 |
| --- | --- |
| 먼저 현장을 동결한다 | checkpoint, optimizer state, 훈련 로그, data manifest, eval raw outputs, 시스템 지표, 관련 commit을 저장한다 |
| 먼저 계층별로 귀인한다 | system, data, eval, model, post-train recipe 중 어느 층이 먼저 변했는지 가린다 |
| 먼저 버킷별로 본다 | 전역 loss가 정상이라고 데이터 버킷, 언어, 길이, 과제가 모두 정상인 것은 아니다 |
| 먼저 guardrail을 보호한다 | 희생 불가 능력이 임계값을 넘어 후퇴하면 목표 능력이 계속 오르기를 기다릴 필요가 없다 |
| 숨은 땜질을 하지 않는다 | 필터, 샘플링 가중치, prompt, harness, judge, decoding 또는 serving config를 바꾸면 모두 experiment_id를 새로 만들어야 한다 |

### 7.2 훈련 중 사고 triage 표

| 사고 유형 | 현장 증상 | 30분 1차 조사 | 계층별 귀인 | 즉시 결정 | 반드시 보관할 것 |
| --- | --- | --- | --- | --- | --- |
| numerical | NaN / Inf / loss 폭발 | 그래디언트 노름, overflow 횟수, LR/warmup, 최근 batch, optimizer state, resume 로그 | system: 정밀도/kernel. data: 불량 샘플. model: LR/clip. checkpoint: resume | 차단. 가장 최근의 건강한 checkpoint로 롤백하고 문제 batch를 replay | `checkpoint_id`, batch id, overflow log, optimizer hash, replay 결과 |
| numerical / model | 단계 전환 후 loss spike | 단계 전환 commit, LR schedule, mix 가중치, 길이 분포, optimizer/RNG의 연속 여부 | data: mix 급변. model: schedule. system: resume. eval: 창 기준 | spike가 설명 가능하고 빠르게 회복되면 관찰. 이상이 지속되면 rollback | phase-change diff, 전후 3개 checkpoint 곡선, data manifest diff |
| infra | 처리량 하락 / GPU 사용률 이상 | tokens/s, MFU, dataloader wait, NCCL, 스토리지 IO, kernel 버전, batch shape | system 우선. 확인 전에는 모델 변화로 해석하지 않는다 | 능력 결론을 보류. 필요하면 run을 멈추고 조사 | system metrics, profile trace, 코드/이미지 버전, 재실행 대조 |
| data | 전역 loss는 정상인데 어떤 버킷의 loss가 이상 | bucket validation loss, sampling weight, tokenizer/packing, manifest diff, 샘플 추출 점검 | data 우선. 그다음 tokenizer/packing과 eval bucket을 본다 | 문제 버킷을 동결하거나 내린다. 심각하면 manifest를 rollback | bucket id, manifest hash, 추출 샘플, 필터 버전, 수정 diff |
| data / capability | 합성 데이터 템플릿화 또는 오류율 상승 | teacher/version, prompt, verifier, template n-gram, response length, 사람 검수 오류율 | data: 생성기. eval: 샘플이 너무 좁음. model: 능력이 아니라 형식을 학습 | synthetic ratio를 낮추거나 버킷을 격리. 형식의 이득을 추론의 이득으로 적지 않는다 | generator config, verifier 버전, 반복률, 사람 검토 기록 |
| capability | 범용 능력의 초기 대폭 후퇴 | base regression max drawdown, 저득점 버킷, 언어/도메인 고정 바구니, 데이터 mix | model: LR/훈련 과장. data: 전용 비율 과다. eval: 표본 추출 편향 | guardrail 발동. 롤백하거나 전용 비율을 낮춘다 | scorecard, 실패 샘플 군집, mix curve, rollback 지점 |
| capability | 목표 능력은 오르는데 guardrail이 악화 | 목표 지표, 희생 불가 능력, 인접 checkpoint, 오류 유형 변화 | model/data의 저울질. eval 기준 변화가 아닌지 확인 | promotion하지 않는다. trade-off를 사업 쪽이 수용하고 재현 가능할 때에만 extend | Pareto 곡선, guardrail 임계값, DRI 서명, 샘플 대조 |
| eval | Eval 급등/급락 | data_hash, harness_commit, prompt/wrapper, judge, decoding, 답안 추출기 | eval 우선. 같은 checkpoint로 신·구 harness diff를 돌린다 | 능력 결론을 동결. 구/신 harness를 교차 재실행 | eval diff, raw outputs, judge 버전, metric 변경 설명 |
| eval / data | Public benchmark는 오르는데 private은 오르지 않음 | contamination report, private holdout, 문제 유형 유사도, raw output | data 오염 또는 eval 과적합. public이 너무 좁을 수도 있다 | primary 지표에서 가중치를 낮춘다. 확대할 수 없다 | contamination 증거, holdout 사용 기록, 제거 샘플 목록 |
| capability / context | Needle은 좋은데 실제 긴 과제가 나쁨 | 긴 과제 raw output, 증거 위치, 정보 밀도, 답변 불가 샘플, 길이 분포 | eval: needle이 너무 좁음. data: 종합/충돌 과제 부족. system: serving 차이 | needle을 주 gate로 삼지 않는다. 긴 훈련 확대를 중지 | 긴 과제 실패 군집, 증거 위치 파악, 길이 버킷 점수, serving 설정 |
| capability / context | 긴 컨텍스트 훈련이 짧은 과제를 해침 | sequence_length_distribution, 짧은 과제 회귀, packing/padding, 짧은 샘플 비중 | data: 긴 샘플에 의한 희석. model: 위치/attention 적응의 부작용 | 길이 mix를 롤백하거나 짧은 샘플 비율을 복원 | 길이 분포 diff, 짧은 과제 scorecard, curriculum 버전 |
| infra / context | 오프라인에서는 긴 컨텍스트가 쓸 만한데 온라인에서는 불가 | serving config, KV cache, chunked prefill, batching, kernel, latency/cost | system 우선. 모델 능력 결론은 미룬다 | 시스템 차단. 출시하지 않으며 온라인 실패를 모델 실패로 기록하지 않는다 | offline/online config diff, 온라인 raw output, profile |
| post-train handoff | Post-train 이후 이득 소멸 | paired protocol, seed, SFT/RL 데이터 버전, checkpoint selection, 훈련 곡선 AUC | post-train recipe 또는 base eval 가짜 양성. mid-train이 불안정할 수도 있다 | 확대하지 않는다. paired run을 반복하거나 목표 데이터로 돌아간다 | recipe hash, seed, A/B 곡선, post-train raw outputs |
| post-train handoff | Reward hacking 증가 | RL raw output, reward/verifier, 거부/안전, 형식 의존, CoT 템플릿 | post-train reward의 허점. mid-train이 형식을 미리 굳혔을 수 있다 | 행동 형식 데이터를 줄인다. reward/verifier를 고친 뒤 재실행 | reward 버전, hacking 샘플, 행동 데이터 비율, 수정 기록 |
| infra | Checkpoint resume 불연속 | resume 전후 loss, optimizer/RNG, data cursor, checkpoint hash, 훈련 코드 버전 | system/checkpoint 우선. 배제한 뒤 data/model을 본다 | rollback. replay resume 테스트 통과 후 run을 새로 만든다 | checkpoint lineage, RNG/data cursor, replay log, 코드 hash |
| eval | Checkpoint 간 결론이 뒤바뀜 | 인접 checkpoint, CI/분산, 다중 seed, selection policy, raw outputs | eval 노이즈 또는 selection 편향. model의 실제 변동은 2차 검증이 필요 | 단일 지점으로 결정하지 않는다. 최고점이 아니라 곡선을 보고한다 | selection policy, 완전한 곡선, 신뢰구간, 실패 샘플 |

### 7.3 데이터 사고 runbook

데이터 사고의 제1원칙은 현장 땜질이 아니라 버전 격리다. 필터, 생성기, 중복 제거, 샘플링 가중치, tokenizer 또는 packing의 어떤 변화든 새로운 data_version과 manifest hash를 만들어야 한다.

| 단계 | 조치 | 종료 조건 |
| --- | --- | --- |
| 1. 동결 | 이전 manifest, 샘플링 가중치, 생성기 설정, 필터 버전, 추출 샘플 저장 | 사고 이전의 데이터 입력을 재현할 수 있다 |
| 2. Diff | token 수, 언어/도메인/길이 분포, 중복률, 오염률, 불량 샘플률 비교 | 이상 버킷을 적어도 하나 설명한다 |
| 3. 격리 | 문제 버킷을 내리거나 가중치를 낮추고, 범용 보전 버킷과 guardrail eval은 유지 | 문제 버킷이 더 이상 계속 훈련에 들어가지 않는다 |
| 4. 재실행 | 고정 checkpoint로 data validation과 linked eval을 재실행 | 수정이 eval 기준 변경이 아니라 데이터에서 왔음을 증명한다 |
| 5. 복기 | 데이터 버킷 진입 카드와 prevention_rule 갱신 | 새 data_version이어야 다음 훈련에 들어갈 수 있다 |

오염, license 또는 프라이버시 경계를 명확히 설명할 수 없으면 해당 데이터 버전을 곧바로 kill해야 한다. mid-train에서 "오염됐을 수 있지만 점수는 좋다"는 수용 가능한 상태가 아니다.

### 7.4 훈련 사고 runbook

훈련 사고는 복구 가능성 보호를 우선한다. numerical 또는 resume류 문제를 발견하면 학습률부터 조정해 운에 맡기지 않는다. 먼저 checkpoint, optimizer, RNG, data cursor, 코드 버전이 replay 가능한지 확인한다.

| 단계 | 조치 | 종료 조건 |
| --- | --- | --- |
| 1. 정지 | incident_id를 표시하고 현재 run을 동결하며 능력 결론을 더 이상 써넣지 않는다 | 현장 로그와 상태가 완전하다 |
| 2. 재생 | 가장 최근의 건강한 checkpoint에서 짧은 창을 재생해 재현 가능한지 확인 | 재현되면 위치를 특정하고, 재현되지 않으면 시스템 불확실성을 기록한다 |
| 3. 단일 변수 수정 | 매번 변수 하나만 바꾼다: LR, clip, precision, bad batch, resume 로직 중 하나 | 수정과 지표 변화를 귀인할 수 있다 |
| 4. 회귀 | 버킷별 loss, base regression, 핵심 target eval을 다시 돌린다 | 새로 추가된 guardrail 사고가 없다 |
| 5. 결정 | kill / retry / rollback / extend / promote | DRI 서명과 증거 경로가 있다 |

훈련을 계속하기 위한 최저 조건은 이렇다: 수치가 안정적이고, 시스템 replay가 성공했으며, 데이터 manifest가 표류하지 않았고, eval harness가 표류하지 않았다. 어느 하나라도 빠지면 retry나 rollback만 가능하고 promote할 수 없다.

### 7.5 평가 사고 runbook

평가 사고에서 가장 흔한 오류는 도구의 변화를 능력의 변화로 여기는 것이다. prompt, wrapper, judge, 답안 추출기, decoding, 샘플셋 또는 metric 중 어느 하나라도 바뀌면 이전 점수와 새 점수는 곧바로 가로 비교할 수 없다.

| 조사 매트릭스 | 이전 checkpoint | 새 checkpoint |
| --- | --- | --- |
| 이전 harness | 과거 기준선 재현 | 모델의 진짜 증분을 본다 |
| 새 harness | 도구 기준의 변화를 본다 | 새 기준의 결과로만 쓴다 |

"이전 harness에서 새 checkpoint가 좋아졌다"와 "새 harness에서 이전 checkpoint가 같은 정도로 좋아지지 않았다"가 동시에 성립할 때에만 이득을 일차적으로 모델에 귀속할 수 있다. private holdout을 반복해서 들여다보았거나 그것으로 파라미터를 조정했다면 dev-private으로 격하하고 sealed-private 또는 final-blind를 새로 구축해야 한다.

### 7.6 Post-train 이어받기 사고

Mid-train의 이득이 post-train 이후 사라지더라도 mid-train이 무효라고 단순 판정하지 않는다. 네 가지를 동시에 조사해야 한다:

| 조사 항목 | 가능한 문제 | 처리 |
| --- | --- | --- |
| recipe가 동결되었는가 | SFT/RL 데이터, seed, 예산, reward/verifier, decoding 변화 | paired protocol 재실행 |
| selection에 편향이 있는가 | post-train 최고점이나 base 최고점만 골랐다 | 고정된 checkpoint selection policy를 쓴다 |
| 능력이 덮였는가 | SFT 스타일 데이터가 목표 능력을 눌렀거나, RL 보상이 단답 또는 형식 쪽으로 치우쳤다 | post-train 데이터/보상을 조정한다면 반드시 experiment_id 또는 paired_protocol_version을 새로 만든 뒤 readiness를 다시 측정한다 |
| 이득이 가짜 양성인가 | base eval 오염, public 과적합, 샘플이 너무 좁음 | 6장 eval registry와 7.5절로 돌아간다 |

**post-train 이어받기가 paired protocol 아래 두 라운드 연속 실패하고, base 쪽 이득이 public benchmark나 단일 seed에만 존재하면 해당 mid-train 방향을 kill해야 한다**. base 쪽 이득은 안정적인데 SFT/RL에 덮였다면 결론을 "post-train handoff가 뚫리지 않았다"로 적고 "mid-train에 이득이 없다"로 적지 않는다. 덮임 문제를 조사하려고 SFT/RL 데이터, reward, verifier, 예산 또는 seed를 조정했을 때는 이전 paired protocol의 결론을 계속 mid-train 이득의 증거로 쓸 수 없고 진단 단서로만 쓸 수 있다.

### 7.7 사고 복기 템플릿

경보 또는 차단 등급의 사고마다 복기 기록이 하나씩 있어야 한다. 복기는 책임 추궁 문서가 아니라 다음 훈련에서 같은 구덩이를 덜 밟게 하려는 것이다.

```text
incident_id:
experiment_id:
incident_type: numerical | data | eval | infra | capability | post-train handoff
severity: observation | alert | blocker
first_detected_at:
affected_checkpoint:
symptom:
root_cause: confirmed | suspected | unresolved
changed_variables:
rollback_point:
evidence_paths:
four_layer_isolation:
  system_replay:
  data_manifest_diff:
  eval_harness_diff:
  model_checkpoint_diff:
decision: kill | retry | rollback | extend | promote | unresolved
prevention_rule:
owner:
reviewed_by:
```

`root_cause`가 여전히 `unresolved`라면 사고는 훈련 조치를 종결할 수 있지만 인식상의 결론은 종결할 수 없다: 문서에는 "미귀인 사고, 격리 완료"로만 적을 수 있고 "모델 능력 퇴화"나 "어떤 데이터 버킷이 유효하다"로 적을 수 없다.

## 8. 신규 팀을 위한 90일 로드맵

이 로드맵은 참고 리듬이지 달력상의 약속이 아니다. **다음 단계 진입은 며칠째인지가 아니라 Gate 0-5가 결정해야 한다.**

### 8.0 Gate dashboard: 각 단계는 의사결정 질문 하나에만 답한다

90일 로드맵의 용도는 일정 짜기가 아니라 프로젝트를 "훈련하고 싶다"에서 "증거가 충분해진 뒤 훈련한다"로 밀고 가는 것이다. 각 gate는 질문 하나에만 답한다:

| Gate | 의사결정 질문 | 필수 증거 | Blocker | Owner | Next action |
| --- | --- | --- | --- | --- | --- |
| Gate 0 | 이 목표에 정말 mid-train이 필요한가 | charter, 희생 불가 능력, v1 eval registry, v1 post-train paired protocol | 목표를 SFT/RAG/제품 로직으로 해결할 수 있음. eval 또는 holdout 미동결 | Model Lead | go / no-go charter |
| Gate 1 | 데이터가 실험에 들어가도 되는가 | data manifest/hash, license, 오염 검사, 표본 검토, linked eval | 데이터 출처 불명확, 합성 생성기가 eval을 읽었음, holdout 유출 | Data DRI | data readiness memo |
| Gate 2 | proxy ablation이 나쁜 방향을 배제했는가 | 목표 이득, 범용 후퇴, 두 scale 또는 target 단기 신호, 실패 샘플 군집 | public benchmark만 오름. 합성 데이터 템플릿화. proxy 결론 불안정 | Eval DRI | ablation decision memo |
| Gate 3 | 주 모델 단기 훈련을 계속할 가치가 있는가 | checkpoint 곡선, 버킷별 loss, scorecard, 사고 기록, Pareto 결과 | NaN/loss spike, resume 불연속, guardrail 선을 넘음, 긴 컨텍스트가 짧은 과제를 해침 | Training Infra DRI | extend / rollback / kill |
| Gate 4 | 이득이 post-train에서 보존될 수 있는가 | paired SFT/RL 결과, seed, AUC, raw outputs, reward/safety 회귀 | base는 오르는데 post-train 이후 사라짐. recipe가 중간에 바뀜. reward hacking 증가 | Post-train DRI | readiness report |
| Gate 5 | 훈련 확대에 들어갈 것인가, 축소해 다시 할 것인가 | go/no-go memo, model registry, rollback checkpoint, 비용 대비 이득 판단 | 이득이 오염/좁은 평가/단일 seed에서 옴. 사고 미귀인. 후퇴를 설명할 수 없음 | Decision owner | scale / shrink / stop |

> [!CAUTION]
> **어떤 gate의 증거가 불완전하다면 "조금 더 훈련해 보자"로 우회하지 않는다.** Mid-train은 프로젝트 비용이 높으며, **진짜 리듬 통제는 달력이 아니라 gate에서 나온다**.

각 gate의 dashboard 기록에는 `status`, `owner`, `evidence_path`, `version_hash`, `stale_after`, `next_action`도 반드시 포함되어야 한다. **증거 경로가 없는 녹색 상태는 황색으로 간주해야 한다.**

### 0-14일차: 목표와 평가 정의

Gate 0에 해당하며 주책임은 Model Lead, Eval DRI, Post-train DRI다. 이 단계의 결정 회의는 질문 하나에만 답한다: 이 목표에 정말 mid-train이 필요한가.

인도물:

- Mid-train charter: 목표 능력, 희생 불가 능력, 목표 checkpoint, 예산.
- Eval matrix: base eval, 능력 eval, 긴 컨텍스트 eval, post-train readiness.
- 데이터 버킷 설계 문서.
- 위험 목록과 go/no-go gate.
- Frozen post-train recipe: SFT/RL 데이터 버전, 훈련 예산, seed, harness, 평가셋, 실패 판정.

Go/no-go:

- eval registry, 비공개 holdout, post-train 이어받기 recipe가 동결되지 않았으면 훈련에 들어가지 않는다.
- 비공개 holdout의 생성 시각이 훈련 데이터 혼합보다 늦거나, 비공개 holdout을 겨냥한 파라미터 조정을 허용하면 훈련에 들어가지 않는다.

### 15-35일차: 데이터와 소형 모델 ablation

Gate 1-2에 해당하며 주책임은 Data DRI와 Eval DRI다. 모든 실험은 4.6의 실험 대장에 등록해야 한다.

인도물:

- 예컨대 1B/3B/7B proxy model에서의 데이터 mix 실험. 구체적 scale은 팀의 기존 모델 계보와 예산이 결정한다.
- 학습률과 token budget sweep.
- 합성 데이터 정확성 및 다양성 보고서.
- 각 데이터 버킷의 loss와 능력 연관 분석.
- Data manifest/hash, near-duplicate 탐지 보고서, 오염 검사 보고서, 사람 표본 검사 샘플.

Go/no-go:

- 적어도 하나의 mix가 목표 능력에서 향상되고 범용 능력 후퇴가 수용 가능하다.
- 합성 데이터에 뚜렷한 오염과 스타일 붕괴가 없다.
- Proxy의 성공은 나쁜 방향이 배제되었음을 말해 줄 뿐 target scale에서 반드시 성립함을 증명하지 못한다. 주 모델 단기 훈련에 들어가기 전에 적어도 두 scale의 방향이 일치하거나 target model 단기 run으로 핵심 신호를 검증해야 한다.

### 36-60일차: 주 모델 단기 mid-train

Gate 3에 해당하며 주책임은 Training Infra DRI, Eval DRI, Model Lead다. 이 단계에서는 반드시 kill switch를 먼저 정의한 뒤 훈련을 착수한다.

인도물:

- 주 모델 단기 훈련, 예컨대 10B-100B token급 창. 구체적 token budget은 Gate 2 증거와 훈련 비용이 결정한다.
- 일일 checkpoint eval.
- 능력/망각 Pareto 곡선.
- 후보 checkpoint 선택.
- 훈련 runbook, checkpoint lineage, resume 기록, 훈련 코드 commit, 사고 기록.

Go/no-go:

- 목표 능력 향상이 단일 benchmark에 의해 이끌린 것이 아니다.
- 범용 능력 하락이 사전에 정의한 임계값보다 낮다.
- 생성 샘플에 뚜렷한 스타일 표류가 없다.
- NaN, 회복 불가능한 loss spike, 그래디언트 이상, 처리량 이상, 어떤 데이터 버킷의 loss 이상, checkpoint resume 불연속이 나타나거나 긴 컨텍스트 훈련이 짧은 과제를 해칠 때는 중단 또는 롤백을 발동한다.

### 61-75일차: post-train 이어받기 검증

Gate 4에 해당하며 주책임은 Post-train DRI와 Eval DRI다. post-train recipe가 이 단계에서 바뀌면 mid-train 결론은 무효로 보거나 실험 ID를 다시 표시해야 한다.

인도물:

- 고정 SFT recipe 대조.
- 해당되는 경우 고정 RL/RLVR recipe 대조.
- post-train 이후 실제 과제 평가.
- reward hacking / safety / style 회귀 보고서.
- Post-train readiness report: recipe 버전, seed, 예산, harness, 실패 판정, 이득 보존 비율.

Go/no-go:

- Mid-trained checkpoint가 post-train 이후에도 이득을 유지한다.
- 정렬 난이도가 뚜렷이 증가하지 않았다.

### 76-90일차: 확대 또는 축소 결정

Gate 5에 해당하며 주책임은 Decision owner, Model Lead, Release owner다. 이 단계는 자동 확대가 아니라 계속, 축소, 데이터 재작업 또는 중단을 결정하는 단계다.

인도물:

- 확대 후보 recipe 또는 다음 단계의 축소 재작업 recipe.
- 100B-1T+ token 훈련에 들어갈지에 대한 결정.
- 데이터와 평가 자동화 개선 목록.
- 긴 컨텍스트 또는 두 번째 능력 목표의 다음 단계 계획.
- Model registry: checkpoint lineage, data manifest, eval raw outputs, 훈련 로그, 권한, 보존 주기, 롤백 가능한 checkpoint.

Go/no-go:

- **이득이 주로 오염, 좁은 평가 또는 post-train의 우연성에서 왔다면 확대하지 않는다.**
- 이득이 안정적이고 설명 가능하며 post-train 이후에도 남는다면 주 훈련에 들어간다.

## 9. 실행 가능한 checklist

### 9.0 최소 인도 묶음과 인도물 색인

팀이 처음부터 완전한 문서 체계를 유지하고 싶지 않더라도 적어도 아래 8개 인도물은 있어야 한다. 어느 하나라도 빠지면 mid-train 결론을 복기하기 어렵다.

| 인도물 | Owner | 템플릿 위치 | 동결 Gate | 어느 회의에서 쓰는가 |
| --- | --- | --- | --- | --- |
| Mid-train charter | Model Lead | 0.2 / 8.0 | Gate 0 | 착수 회의, go/no-go 회의 |
| Data manifest | Data DRI | 4.2.1 / 9.1 | Gate 1 | 데이터 readiness 회의, 사고 복기 |
| Eval registry | Eval DRI | 6.1 / 9.3 | Gate 0-1 | eval freeze 회의, checkpoint review |
| Training runbook | Training Infra DRI | 4.3.1 / 5 / 7.4 | Gate 3 | train launch 회의, 사고 처리 |
| Experiment ledger | Model Lead / PM | 4.6 | Gate 0 이후 지속 갱신 | 주간 실험 정례회의 |
| Checkpoint scorecard | Eval DRI | 6.7 | Gate 3-5 | checkpoint review, 확대 결정 |
| Post-train readiness report | Post-train DRI | 6.6 / 7.6 | Gate 4 | post-train handoff 회의 |
| Incident review | 사고 owner | 7.7 | 경보/차단 사고 이후 | 사고 복기, prevention review |
| Go/no-go memo | Decision owner | 8.0 / 9.4 | Gate 5 | 확대, 축소 또는 중단 결정 |

Checklist의 역할은 이 인도물들을 검수하는 것이지 절차 부담을 만드는 것이 아니다. 신규 팀에게는 완벽한 플랫폼을 추구하기보다 먼저 최소 인도 묶음을 끝까지 돌려 보는 것이 더 중요하다.

각 checklist 항목은 체크 표시만 해서는 안 되고 최소 감사 필드를 묶어야 한다:

```text
owner:
evidence_path:
version_hash:
stale_after:
gate_role: primary | guardrail | diagnostic
status: green | yellow | red
```

어떤 점검 항목에 `evidence_path`나 `version_hash`가 없으면 그것은 많아야 yellow이며 gate 통과 증거로 쓸 수 없다.

### 9.1 데이터 checklist

- [ ] 각 데이터 버전에 data manifest/hash가 있고 source snapshot, processing commit, tokenizer, dedup, contamination, sampling weight, shuffle seed를 기록한다.
- [ ] 각 데이터 소스에 license / 컴플라이언스 기록이 있다.
- [ ] 각 데이터 버킷에 품질 점수와 사람에 의한 샘플 검토가 있다.
- [ ] 각 데이터 버킷이 linked_eval_id에 묶여 있으며, eval에 묶이지 않은 버킷은 샘플링 가중치를 높이지 않는다.
- [ ] benchmark contamination 검사가 완료되었다.
- [ ] 훈련셋, 검증셋, 비공개 holdout이 분리되어 있다.
- [ ] 합성 데이터는 teacher/version, prompt, 샘플링 파라미터, verifier, 필터링 규칙, 거부 샘플 비율, 템플릿 반복률, 사람 검수 오류율을 기록한다.
- [ ] 합성 데이터에 정확성 필터링, 다양성, 템플릿화, style entropy 검사가 있다.
- [ ] 긴 컨텍스트 데이터가 이어 붙인 텍스트만이 아니라 실제 긴 과제를 포함한다.
- [ ] 범용 데이터 유지 비율이 ablation으로 뒷받침된다.

### 9.2 훈련 checklist

- [ ] Base checkpoint eval이 완료되었다.
- [ ] Tokenizer / special tokens가 동결되었거나 변경에 충분한 이유가 있다.
- [ ] Optimizer state 이어받기 전략이 명확하다.
- [ ] LR schedule, warmup, peak/min LR, decay shape, gradient clipping, precision이 명확히 기록되어 있다.
- [ ] global batch, microbatch, packing/masking, data order, shuffle seed가 명확히 기록되어 있다.
- [ ] checkpoint selection policy가 훈련 전에 동결되었다.
- [ ] 각 단계에 checkpoint 저장 전략이 있다.
- [ ] 버킷별 validation loss를 관측할 수 있다.
- [ ] MoE/attention/long-context 시스템 지표를 관측할 수 있다.
- [ ] 훈련을 resume할 수 있고 checkpoint를 재현할 수 있다.

### 9.3 평가 checklist

- [ ] Eval registry가 동결되었고 eval_id, eval_family, data_hash, harness_commit, prompt_or_wrapper_version, metric, decision_role, threshold_or_guardrail, raw_output_path를 포함한다.
- [ ] Base eval, 능력 eval, 긴 컨텍스트 eval이 분리되어 있다.
- [ ] 각 eval에 primary, guardrail 또는 diagnostic이 표시되어 있고 primary 지표는 3-5개를 넘지 않는다.
- [ ] 지표에 실제 과제와 사람 검토가 포함된다.
- [ ] 평균 점수만 보지 않고 능력 후퇴도 본다.
- [ ] 각 후보 checkpoint에 대해 scorecard를 생성하며, 목표 능력 delta, 최대 후퇴, 오염 상태, 실패 샘플, 권고 조치를 포함한다.
- [ ] 각 후보 checkpoint에 동일한 eval 한 벌을 수행한다.
- [ ] 비공개 holdout은 dev-private, sealed-private, final-blind로 나뉘고, 생성 시각이 훈련 데이터 mix 동결보다 이르며, sealed/final을 겨냥해 파라미터를 조정해서는 안 된다.
- [ ] 긴 컨텍스트 eval이 길이, 위치, 정보 밀도, 과제 유형, 배포 일관성을 커버한다.
- [ ] Post-train 이어받기 recipe가 고정되어 있고 데이터 순서, seed, harness, 예산, checkpoint selection policy, 실패 판정을 기록한다.
- [ ] Post-train 이후의 이득을 재현할 수 있다.

### 9.4 조직 checklist

- [ ] 데이터 팀, 훈련 팀, Post-train DRI가 같은 실험 대장을 공유한다.
- [ ] 매 실험마다 데이터 mix, LR, token budget, context length, eval 버전을 기록한다.
- [ ] Research, Data, Training, Eval, Post-train, Release owner가 모두 명확하다.
- [ ] Model Lead, Data DRI, Training Infra DRI, Eval DRI, Post-train DRI, Safety/Compliance DRI, Product/Domain DRI, Decision owner가 모두 명확하다.
- [ ] Mid-train charter, data manifest/hash, eval registry, runbook, checkpoint ledger, post-train readiness report, go/no-go memo에 모두 owner가 있다.
- [ ] 프로젝트 시작 전에 "희생 불가 능력"과 각 단계의 롤백 조건을 동결한다.
- [ ] 각 gate의 임계값, 차단 조건, 서명자가 실험 전에 gate memo에 기입되어 있다.
- [ ] 중간에 mix, 필터, eval 버전을 바꾸는 모든 행위는 experiment_id를 새로 만든다.
- [ ] 훈련 중 중단 조건이 있다.
- [ ] 훈련 확대 전에 반드시 go/no-go gate를 통과한다.
- [ ] 출시 전에 pre-mid, mid, post 세 종류 checkpoint의 완전한 보고서와 model registry를 보존한다.

## 10. post-train 경험이 있는 기반 모델 팀에 대한 특별 당부

첫째, **SFT의 사고방식으로 mid-train을 하지 않는다**(상세는 1.2, 1.4 참조). Mid-train 데이터에는 QA, CoT, 코드 과제가 포함될 수 있지만 그 목표는 모델이 제품 답변 형식을 익히게 하는 것이 아니라 능력 분포를 바꾸는 것이다. **자가 점검: 데이터 mix의 대부분이 지시-답변 쌍이라면 능력 조형이 아니라 앞당긴 SFT를 하고 있을 가능성이 높다.**

둘째, **RL에 모든 책임을 떠넘기지 않는다**(상세는 2.4의 넷째, 6.6 참조). base model에 충분한 수학, 코드, 긴 컨텍스트, 자기 교정 substrate가 없으면 RL은 표면적 탐색이나 장황한 추론만 익힐 가능성이 높다. **자가 점검: 목표 과제의 zero-shot pass@100이 0이라면 능력이 base의 도달 가능 경계 안에 없다는 뜻이며, RL은 높은 확률로 정답을 안정적으로 탐색해 내지 못한다.**

셋째, **리더보드만 쫓지 않는다**(상세는 6.4, 7.2 eval 사고, 8.0 참조). Mid-train의 진짜 이득은 비공개 과제, 실제 제품 과제, post-train 이어받기에서 동시에 성립해야 한다. **자가 점검: 어떤 eval의 이득이 5%포인트를 넘는데 비공개 holdout이 움직이지 않으면 먼저 오염이나 형식 적응을 가정한다.**

넷째, **처음부터 1M context를 쫓지 않는다**(상세는 4.5 참조). 대다수 팀에게는 극단적으로 긴 context를 시연하는 것보다 먼저 32K/128K를 믿을 만하게 만드는 것이 더 현실적이다. **자가 점검: 짧은 과제(<4K) 성능이 길이를 늘린 뒤 뚜렷이 떨어지면 context extension의 비용이 아직 통제되지 않았다는 뜻이다.**

다섯째, **데이터 엔지니어링을 소홀히 하지 않는다**(상세는 4.2, 4.2.1, 9.1 참조). Mid-train 프로젝트에서 훈련 코드는 흔히 병목이 아니며, 데이터 lineage, 오염 통제, 버킷별 eval, 실험 규율이 병목이다. **자가 점검: 팀이 현재 훈련에 쓰는 data manifest hash와 오염 검사 버전을 30초 안에 말하지 못하면 데이터 거버넌스가 아직 자리 잡지 못한 것이다.**

## 11. 1차 라운드 탐색 공간: 예시 탐색 그리드이며 기본 mix로 직접 쓸 수 없다

이 장은 작업 예시이지 배합이 아니다. 그 용도는 mid-train을 처음 하는 팀이 데이터, 훈련, 평가, post-train 이어받기를 하나의 최소 증거 사슬로 꿰도록 돕는 것이다("최소 폐루프"의 정의는 4.0 참조).

팀에 이미 쓸 만한 base model과 안정적인 post-train pipeline이 있다면, 1차 라운드에서는 크고 전면적인 것을 하지 말고 먼저 "능력형 mid-train + post-train 이어받기"의 최소 폐루프를 만들기를 권한다. 아래 비율은 추천 recipe가 아니라 ablation 착수를 위한 탐색 공간이다. 모델 규모, 사전훈련 이력, 목표 언어, 제품 과제가 다르면 최적 mix가 뚜렷이 달라지며, 주 훈련 전에 반드시 proxy scale과 단기 주 모델 검증을 통과해야 한다. 아래의 비율과 token 구간은 ablation 변수 설계에만 쓰며 기본 mix, 기본 LR 또는 기본 예산으로 삼아서는 안 된다.

base checkpoint, 목표 능력, 희생 불가 능력, eval registry, data manifest, post-train paired protocol이 동결된 뒤에야 아래 구간을 ablation 변수로 쓸 수 있다. 그렇지 않으면 훈련 설정에 들어가서는 안 된다.

목표:

- 수학, 코드, STEM, 복잡한 QA를 높인다.
- 범용, 다국어, 사실, 자연 생성을 뚜렷이 해치지 않는다.
- SFT/RL 이후에도 이득이 있는지 검증한다.

데이터 mix 탐색 공간(bucket sensitivity sweep 축):

- 고품질 범용 텍스트: 저/중/고 몇 개 지점으로 보전 하한선을 시험한다. 예컨대 30/50/70%이며 고정 비중 제안이 아니다.
- 코드와 FIM: 저/중/고 몇 개 지점으로 코드 능력과 일반 생성 표류를 시험한다. 예컨대 10/20/30%.
- 수학/STEM: 저/중/고 몇 개 지점으로 추론 주입 이득, 포화점, 범용 후퇴를 시험한다.
- 합성 교재/검증 가능한 추론: 상한 sweep으로 verifier 품질, 템플릿화, teacher 오류 증폭을 시험한다.
- QA/CoT/단답 과제 형태: 별도 스위치 또는 낮은 비율 혼입으로 형식 표류를 시험해, post-train 행동 형식을 미리 굳히는 것을 피한다.

이 bucket 축들은 1차 라운드의 단일 변수 또는 소수 변수 탐색에만 쓰며, 동시에 충족해야 하는 정규화 비율표가 아니다. 실제 mix는 반드시 소형 모델과 단기 주 모델 실험으로 결정해야 한다.

이 출발점은 어떤 공개 모델의 복제 배합도 아니고 공개 보고서에서 역추론한 최적 비율도 아니다. 신규 팀이 데이터 충돌, 망각 위험, 합성 데이터 경계를 드러내기 쉽게 해 주는 탐색 그리드 한 벌일 뿐이다.

주 훈련 전에는 가장 좋아 보이는 지점 하나를 고르는 것이 아니라 반드시 mix sensitivity curve가 있어야 한다. 적어도 다음에 답한다:

- 범용 데이터 비율이 내려갈 때 어떤 희생 불가 능력이 가장 먼저 후퇴하는가?
- 수학/STEM 또는 코드 비율을 높일 때 이득은 선형인가, 포화하는가, 반전하는가?
- Synthetic ratio가 늘 때 비공개 과제, 스타일 검토, 템플릿 반복률이 함께 악화하는가?
- 같은 mix가 서로 다른 seed나 인접 checkpoint에서 방향이 일치하는가?
- 목표 능력 이득이 범용 후퇴와 훈련 비용을 보상하기에 충분한가?

1차 라운드에서 mix 하나만 돌리지 않는다. 더 나은 방법은 control mix 하나를 남겨 두고 단일 변수를 중심으로 작은 매트릭스를 만드는 것이다:

| 변형 | 무엇을 바꾸는가 | 무엇을 바꾸지 않는가 | 목적 |
| --- | --- | --- | --- |
| Control | 저위험 범용 보전 mix | LR, token budget, context length | 회귀 하한선 수립 |
| Math/STEM up | 수학/STEM만 높인다 | 코드, 범용, LR 불변 | 추론 주입 이득과 망각의 대가 판단 |
| Code/FIM up | 코드/FIM만 높인다 | 수학, 범용, LR 불변 | 코드 능력과 일반 생성 표류 판단 |
| Synthetic cap | synthetic 상한을 제한한다 | 다른 버킷 불변 | 합성 데이터가 템플릿화를 가져오는지 판단 |
| General retain | 고품질 범용 데이터를 높인다 | 목표 버킷 불변 | 범용 보전이 후퇴를 줄일 수 있는지 판단 |
| LR lower | LR만 낮춘다 | 데이터 mix 불변 | 데이터 문제와 최적화 문제를 구분 |

각 변형은 주변수 1-2개만 바꿀 수 있다. 훈련하면서 mix, 필터, LR 또는 eval 버전을 바꾸면 실험을 설명할 수 없게 된다.

Gate 2 통과 후의 주 모델 단기 검증 출발점:

- 낮은 학습률로 계속 훈련한다.
- 먼저 원래의 context length 또는 소폭 확장을 쓴다.
- 10B-50B tokens급이 단기 주 모델 검증의 상한 예시다. 실제 예산은 반드시 proxy 결과, target model 단기 신호, 망각 임계값, 비용이 함께 결정해야 한다.
- token의 10%-20%마다 checkpoint를 저장하고 eval한다.

평가 출발점:

- Base eval: MMLU/MMLU-Pro, BBH, GPQA, GSM8K/MATH, HumanEval/MBPP, 다국어 셋.
- 비공개 eval: 내부 수학, 코드, 복잡한 QA, 실제 사용자 과제.
- Post-train readiness: 고정 SFT recipe로 pre-mid와 mid checkpoint를 비교한다.

이번 폐루프에서 안정적인 이득이 없다면 서둘러 token budget을 키우지 않는다. 먼저 데이터와 학습률로 돌아간다.

### 12.4 권장 읽기 순서

1. 먼저 목표 모델 계열의 최신 보고서를 읽는다. 목표 계열이 없으면 먼저 Qwen3와 DeepSeek-V3를 읽는다.
2. 1M/초장 컨텍스트를 할 때에만 Qwen2.5-1M을 보충해 읽는다.
3. 명확한 mid-training 거버넌스 패러다임이 필요할 때에만 OLMo 2를 보충해 읽는다.
4. 합성 데이터가 주변수일 때에만 Phi-4를 보충해 읽는다.
5. late-stage/annealing 공개 세부 사항이 필요할 때에만 Llama 3를 보충해 읽는다.
6. 마지막으로 survey, PRISM, pre/mid/RL 논문을 읽고 메커니즘 가설을 자신의 ablation으로 바꾼다.
